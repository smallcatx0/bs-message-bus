# 开发流程规范

> 本文档定义本项目的开发流程与文档治理规则：任何一个人（或 AI）读完基础文档后，能立即掌握项目上下文、快速进入工作。本文档是 D01，也是该流程规则落地的首个示范样本。

## 1. 问题

项目处于从架构设计向分阶段实施过渡的阶段，存在以下痛点：

- 现状、进度、想法、历史决策混杂，缺乏统一入口，新加入的协作者（含 AI）需要翻遍 `docs/` 才能拼出上下文；
- 迭代完结后设计文档、讨论记录与"当前该做什么"混在一起，越积越乱，噪音淹没现状；
- 缺乏明确规则约束"同一件事只记一处"，导致信息在多处复制、彼此冲突、难以维护。

## 2. 规则与约束

- 遵循 [../项目规范.md](../项目规范.md)：本流程属项目级工程决策，需与该规范保持一致，冲突条款在第 10 节同步修订（见本次改动）。
- 核心原则：**同一事只记一处，别处用相对路径链接引用**，禁止跨文件复制正文。
- `docs/history/` 为已完结迭代归档区，**默认不主动读取**，仅显式追溯历史时可读，避免历史噪音污染当前上下文。

## 3. 方案与决策记录

### 3.1 四类信息归属三个工作区文件 + 一个归档目录

| 信息类型 | 归属位置 | 定位 |
| --- | --- | --- |
| 当前状态、已知问题、下一步 | `curr.md`（仓库根） | 唯一现状入口，简短干练，不堆技术辞藻 |
| 想法、未来规划、暂不做的方向 | `plan.md`（仓库根） | 候选清单，条目化；决定启动时才升级为设计文档 |
| 每次改动的设计（问题/规则/状态上下文） | `docs/<需求名>-design.md`（主干中文） | 每份一个全局递增编号 D01、D02…，编号写在文档首行 HTML 注释，不进文件名 |
| 已完结迭代归档 | `docs/history/` | 设计文档 + 讨论/变更记录一并移入；默认不主动读取 |

### 3.2 生命周期（状态机）

```text
想法 → plan.md 待办条目
     → 用户决定启动：对齐期望 → 创建设计文档 Dnn（docs/）→ curr.md 登记"进行中"
     → 开发期间：设计文档记决策，curr.md 实时更新状态/已知问题/下一步
     → 验收完成：plan.md 勾除条目并注明结论（链接设计文档）
                → curr.md 更新摘要
                → 设计文档（连同讨论/变更记录）移至 docs/history/，修正文内相对链接
```

### 3.3 AI 开工读取顺序

进入工作区按 `AGENTS.md` → `../项目规范.md` → `curr.md` → 当前进行中的设计文档 的路径获取上下文；不主动读取 `docs/history/`。

### 3.4 与既有架构蓝本的关系

`docs/分布式消息总线架构设计.md`（V1）、`docs/分布式消息总线架构演进V2.md` 定位为**长期参考蓝图**，保持原位、不参与 Dnn 编号体系、不归档；V2 属"当前不做"方向，仅在 `plan.md` 留一行链接引用。

### 3.5 关键决策记录

- **文件位置**：`curr.md`/`plan.md` 置于仓库根，让协作者进入工作区第一眼可见；设计文档置于 `docs/`，与蓝图区分。
- **命名**：沿用 `curr.md`/`plan.md` 英文名 + `<中文主干>-design.md`（`-design` 为技术后缀，主干仍中文），需在项目规范第 10 节补充豁免条款。
- **归档目录合法性**：`docs/history/` 是刻意的生命周期归档，不同于第 10 节所禁止的"按分支命名的归档子目录"，需在该节补充说明。

## 文件模板骨架

`curr.md`（三段式，每段条目化、数行以内，不堆技术辞藻）：

```markdown
# 当前状态
- 进行中：Dnn [需求名]（docs/[需求名]-design.md）；已完成摘要…
# 已知问题
- …
# 下一步
- …
```

`plan.md`（条目化候选清单）：

```markdown
- [ ] 一句话想法 —— 备注/触发条件
- [x] ~~某条目~~ → 结论：…，详见 docs/history/xxx-design.md（Dnn）
```

`docs/需求名称-design.md`（首行编号注释，主干中文命名）：

```markdown
<!-- Dnn | 状态：草稿/进行中/已完成 -->
# 需求名称
## 问题
## 规则与约束
## 方案与决策记录
## 状态勾点（关键里程碑）
## 验收结论
```
