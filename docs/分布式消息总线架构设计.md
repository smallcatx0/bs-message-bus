# 分布式消息总线架构设计

> 本文档从 `docs/desc.txt` 的原始需求出发，给出中台化分布式消息总线的整体架构设计，作为后续分阶段实施的蓝本。
> 遵循 `项目规范.md`：本文只做**设计**，不含实现代码；文中接口/表结构均为草图，落地以实施阶段的代码与 DDL 为准。
> 所有未决项统一收敛在第 14 章「假设与待确认」。

---

## 1. 背景与目标

### 1.1 背景（摘自 `docs/desc.txt`）

面向以 **PHP 为主、无常驻内存**的业务线，统一收口 RocketMQ 对接的**分布式消息总线**：以中台模式提供易用 SDK、中心统一消费回调与 BinLog 变更订阅，避免 40+ 业务项目重复造轮子对接消息队列。

### 1.2 核心矛盾与设计支点

- **矛盾**：PHP-FPM 是请求级生命周期，跑不了长连接的 MQ 消费者；但它能正常收发 HTTP。
- **支点**：把 MQ 侧的全部复杂性（连接、消费、重试、路由、位点）**收口到 Go 常驻中台**，业务侧只面对两件事——**发 HTTP（生产）** 与 **收 HTTP 回调（消费）**。

### 1.3 目标能力

| 编号 | 能力 | 说明 |
| --- | --- | --- |
| G1 | 生产 SDK + 中心消费回调 | 封装易用接入屏蔽 RocketMQ 复杂度并统一消息格式；中心统一消费 + 按配置回调各服务 |
| G2 | BinLog 变更订阅 | 基于 Canal 监听 MySQL binlog，按配置规则将数据变更回调到对应业务 |
| G3 | 配置中心热插拔 | 监听、暂停消息、回调路由均由配置中心动态下发，无需发版 |

### 1.4 非目标（边界之外）

- **鉴权 / 限流**：由上游 API 网关统一负责，**服务内不实现相关中间件**（既有工程规范）。
- **业务语义处理**：中台只做「路由 + 投递」，不理解也不改写业务负载内容。
- **消息持久化存储**：消息主体持久化交由 RocketMQ；中台仅持久化投递记录/死信/幂等/配置。

## 2. 设计原则、约束与技术选型

### 2.1 工程规范约束（对齐 `项目规范.md`）

- **日志**：统一 `go.uber.org/zap`，经 `pkg/logger` 工厂接入；必须携带 `trace_id`、脱敏后的关键参数、业务 ID、`latency_ms`。禁止自行构造日志实例。
- **指标**：Prometheus，覆盖请求延迟、请求数量、错误率、goroutine 数、队列深度。
- **错误处理**：错误信息携带调试上下文但**敏感字段必须脱敏**（手机号/邮箱/密码/token/证件号）；返回外部的错误不透传内部实现细节（SQL/堆栈/下游地址）；按业务错误/系统错误/可恢复错误/致命错误四类分治。
- **并发与超时**：并发编排优先 `errgroup.WithContext` + `SetLimit`；**每个 goroutine 必须 panic recover** 并记录堆栈与上下文；**所有外部调用（HTTP、DB、RPC、MQ）必须显式超时**。
- **性能**：热点路径减少 slice 重复扩容/字符串复制/临时对象，并配 benchmark；连接池显式配置容量与超时。
- **测试**：核心逻辑覆盖率 `>= 85%`，覆盖单元/并发/边界。
- **运行时**：优雅关闭（SIGINT/SIGTERM → 停止接收 → 等待在途完成 → 释放资源）；12-Factor，配置来自环境变量、服务无状态、容器友好。
- **结构**：`cmd/` 只做装配；`internal/` 按领域分包、禁止循环依赖；`pkg/` 只放无业务依赖的通用代码。

### 2.2 架构原则

1. **抽象隔离外部依赖**：`broker`（RocketMQ）、`config`（配置中心）、`store`（MySQL/Redis）全部接口化，实现可替换、可 mock、可单测。
2. **单一职责、小而聚焦**：分发（dispatcher）与回调投递（callback）分离；模型（envelope）与传输解耦。
3. **无状态可水平扩展**：实例不持本地状态，幂等/记录走共享存储；消费按 consumer group 分担。
4. **至少一次 + 幂等**：投递语义 at-least-once，以 `msg_id` 幂等去重兜底重复。
5. **配置驱动、热插拔**：监听/路由/暂停全部由配置中心动态下发，内存路由表原子替换、无需发版。
6. **CDC 复用主链路**：Canal binlog 统一转成 Envelope，与 MQ 消息共用同一套路由/投递/死信逻辑，避免两套分发。

### 2.3 技术选型（锁定决策）

本表为经确认的架构选型基线，后续实施不得擅自偏离；变更需同步修订本表与相关模块设计。

| 事项 | 决策 |
| --- | --- |
| 语言/运行时 | Go 1.23+（现状 `go.mod` 1.23.1） |
| 生产端接入 | **双形态**：Go SDK（`pkg/sdk`）+ HTTP 发布网关（`internal/gateway`） |
| Broker | RocketMQ **5.x**，客户端 `apache/rocketmq-clients/golang`（gRPC） |
| CDC 接入 | **Canal → RocketMQ 专用 topic**，复用 broker/dispatcher，不做 TCP 直连 |
| 配置中心 | 自研 **gRPC** 服务；`internal/config` 先做 `ConfigSource` 接口抽象 + 占位实现（本地/静态），gRPC 契约后期对齐（标 TODO，见第 14 章） |
| 投递语义 | **at-least-once + 幂等（msg_id 去重）+ 重试退避 + DLQ**；不保证顺序，分发全并发 |
| 鉴权/限流 | 由上游 API 网关统一负责，**服务内不实现中间件**（既有规范），文档划为边界外 |
| 日志/指标 | 复用 `pkg/logger`（zap）；补 Prometheus（规范第 1 节：延迟/数量/错误率/goroutine/队列深度） |
| 配置解析/存储 | viper（现状）；MySQL（投递记录/DLQ/路由配置持久化）+ Redis（幂等热去重） |
| 并发编排 | `errgroup.WithContext` + `SetLimit`（`golang.org/x/sync`） |
| CDC 组件 | Canal（MySQL binlog 订阅），经 RocketMQ 投递 |

## 3. 整体架构

### 3.1 分层架构图

```text
        ┌──────────────── 上游 API 网关（鉴权 / 限流，边界外）────────────────┐

  PHP 业务 ──HTTP──▶  接入层  internal/gateway  （发布 API）
  Go  业务 ──pkg/sdk─▶           │  校验 · 组装 Envelope（生成 msg_id / trace_id）
                                 ▼
                          适配层  internal/broker  （RocketMQ 5.x gRPC）
                                 │  Producer                    ▲ Consumer
                                 ▼                               │
                       ┌──────────────  RocketMQ 集群  ──────────────┐
                       │   业务 topic            canal topic         │
                       └──────────────────────────────────────────────┘
                                 ▲                       │
   MySQL ──binlog──▶ Canal ──────┘（投递到 canal topic）   │
                                                         ▼
                          核心  internal/dispatcher （分发引擎）
                                 │  路由匹配 · 暂停判定 · 并发回调 · 重试 · 幂等 · DLQ
                                 ▼
                          投递  internal/callback ──HTTP──▶  各 PHP 业务服务
                                 ▲
                          控制面 internal/config （ConfigSource 抽象 + gRPC 占位）
                                 ▲  watch：监听 / 路由 / 暂停 热下发
                          自研配置中心（gRPC）

   持久化 internal/store：MySQL（投递记录 / DLQ / 配置持久） + Redis（幂等热去重）
   横切：pkg/logger（zap） · Prometheus 指标 · trace_id 全链路贯穿
```

### 3.2 组件职责一览

| 组件 | 层 | 职责 | 主要依赖 |
| --- | --- | --- | --- |
| `internal/gateway` | 接入层 | 对外 HTTP 发布 API，校验、组装 Envelope、转投 broker | envelope, broker |
| `pkg/sdk` | 接入层 | Go 生产者易用库，屏蔽接入细节（HTTP 网关 / 直连 broker） | 无 internal 依赖 |
| `internal/broker` | 适配层 | RocketMQ 5.x gRPC 收发，Producer + Consumer 抽象 | envelope |
| `internal/dispatcher` | 核心 | 消费消息 → 路由 → 并发回调 → 重试/幂等/DLQ → ack | config, callback, store |
| `internal/callback` | 投递 | HTTP 回调客户端，向订阅方投递并处理超时/重试 | envelope |
| `internal/canal` | CDC | 消费 canal topic，解析 binlog → Envelope | envelope, dispatcher |
| `internal/config` | 控制面 | 配置中心抽象 + 内存路由表热更新（原子替换） | 无 |
| `internal/store` | 持久化 | 投递记录 / DLQ / 幂等去重 / 配置持久 | envelope |
| `internal/envelope` | 模型 | 统一消息模型与编解码（最底层，无依赖） | 无 |
| `internal/metrics` | 横切 | Prometheus 指标采集与注册 | 无 |

## 4. 核心数据流（四条时序）

### 4.1 生产流（G1 生产端）

```text
PHP: POST /v1/publish {topic, tag, biz_key, headers, payload}
  → gateway 校验参数（脱敏日志）
  → envelope.New：生成 msg_id（雪花/ULID）、trace_id、timestamp，组装 Envelope
  → broker.Producer.Send(ctx, envelope)（显式超时）
  → RocketMQ 业务 topic
  → 返回 {msg_id, trace_id}

Go:  sdk.Publish(ctx, msg)
  → 传输模式二选一：HTTP 网关（默认，零 internal 耦合） / 直连 broker（可选）
  → 后续同上
```

要点：`trace_id` 在入口生成（或透传上游网关带入的），随 Envelope 进入 MQ，为后续消费/回调全链路追踪锚点。

### 4.2 中心消费回调流（G1 消费端，核心）

```text
RocketMQ 业务 topic
  → broker.Consumer（consumer group）拉取消息
  → dispatcher.Handle(ctx, envelope)：
      1. 解析 Envelope
      2. 幂等检查：store.IdempotencyStore.Seen(msg_id, subscriber_id)
      3. 暂停判定：config 快照中 Pause 是否命中 topic/tag/subscriber
      4. 路由匹配：config 快照中 Envelope → subscriber 列表
      5. 并发回调：errgroup.WithContext + SetLimit，逐 subscriber 调 callback.Deliver（各自超时）
      6. 结果处理：
         - 成功 → store 记录投递 + 幂等 Mark
         - 可重试失败（网络/5xx/超时）→ 指数退避重试，未超上限继续
         - 不可重试失败（4xx）或超重试上限 → 进 DLQ（死信 topic + store 记录）
      7. 全部 subscriber 成功（或已入 DLQ）→ 返回成功 → broker ack
         仍有未决（如临时故障）→ 不 ack → RocketMQ 重投（幂等兜底去重）
```

### 4.3 Canal 订阅流（G2）

```text
MySQL binlog → Canal → 投递到 RocketMQ canal topic（Canal 的 MQ 投递模式）
  → broker.Consumer（canal group）拉取
  → canal.Parse：解析 Canal 消息（默认 JSON FlatMessage）
      → 提取 db / table / eventType / before / after / pk / execTime
      → 组装 Envelope{Kind: binlog, Source: "canal", Payload: BinlogEvent}
  → dispatcher.Handle：路由匹配按 db.table + event → 并发 HTTP 回调业务
  → 失败/重试/DLQ 逻辑与 4.2 完全一致（复用）
```

要点：Canal 不直连，统一经 RocketMQ，与主链路共用 broker/dispatcher/callback/store，只多一个 `canal.Parse` 前置解析步骤。

### 4.4 配置热插拔流（G3）

```text
自研配置中心（gRPC）变更监听/路由/暂停
  → config.ConfigSource.Watch(ctx) 收到 ConfigEvent
  → 校验合法性（结构/引用完整性/endpoint 格式）
  → 基于新 Config 重建内存 RoutingTable
  → atomic.Pointer[RoutingTable].Store(newTable)（原子替换）
  → dispatcher / broker 下一次读取 Snapshot() 即生效（无锁、无重启）

占位阶段（gRPC 契约未定）：fileSource（本地 yaml + fsnotify 监听）或 staticSource（内存静态）
```

要点：`ConfigSource` 是抽象接口，占位实现与 gRPC 实现可无缝替换；「无需发版创建监听/暂停」由配置变更 → 原子替换路由表实现。新增 Listener 涉及 broker 运行时动态订阅，见第 7.4 节。

## 5. 统一消息模型 Envelope

`internal/envelope` 定义的统一信封，**生产、中心消费、Canal 三条流共用**，是「统一消息格式」的落点。

### 5.1 Envelope 结构（草图）

```go
// Envelope 消息总线统一信封，贯穿生产→消费→回调全链路。
type Envelope struct {
    MsgID     string            // 全局唯一，幂等键（雪花/ULID，见第 14 章 TODO）
    TraceID   string            // 链路追踪 ID，全链路透传
    Topic     string            // 业务主题（canal 场景可为 db.table 派生）
    Tag       string            // 二级过滤标签（可空）
    BizKey    string            // 业务键（可选，用于查询/未来顺序分区）
    Source    string            // 来源：生产者应用名 或 "canal"
    Kind      MessageKind       // 消息类型：business | binlog
    Timestamp int64             // 生产时间（Unix 毫秒）
    Headers   map[string]string // 透传头（含回调需带的业务标识）
    Payload   []byte            // 业务负载（JSON）；binlog 场景为 BinlogEvent 序列化
}

type MessageKind string
const (
    KindBusiness MessageKind = "business"
    KindBinlog   MessageKind = "binlog"
)
```

### 5.2 BinLog 事件结构（`Kind == binlog` 时 Payload 内容）

```go
// BinlogEvent Canal 解析后的数据变更事件。
type BinlogEvent struct {
    DB        string          // 库名
    Table     string          // 表名
    EventType string          // INSERT | UPDATE | DELETE
    Before    json.RawMessage // 变更前镜像（UPDATE/DELETE 有值）
    After     json.RawMessage // 变更后镜像（INSERT/UPDATE 有值）
    PK        string          // 主键值（幂等/查询/未来顺序键）
    ExecTime  int64           // binlog 执行时间（Unix 秒）
}
```

### 5.3 编解码约定

- **序列化**：Envelope 整体 JSON 编码作为 RocketMQ message body。
- **属性透传**：`trace_id`、`msg_id`、`kind` 等关键头同时写入 RocketMQ message properties，便于消费端不解析 body 即可路由/追踪。
- **接口草图**：
  ```go
  func New(topic, tag string, payload []byte) *Envelope // 自动填充 msg_id/trace_id/timestamp
  func Encode(e *Envelope) ([]byte, error)
  func Decode(data []byte) (*Envelope, error)
  ```
- **wire 契约稳定性**：`pkg/sdk` 不能 import `internal/envelope`（规范第 9 节），故 Envelope 的 JSON schema 是**跨边界稳定契约**，SDK 侧按同一 schema 独立定义结构体序列化；schema 变更需同步 SDK 与本文档。

## 6. 模块设计

每个模块给出：职责、关键接口/类型（草图）、依赖方向。所有接口以「可 mock、可单测」为设计前提。

### 6.1 `internal/envelope`（消息模型，最底层）

- **职责**：定义统一 Envelope 与 BinlogEvent，提供编解码、`msg_id`/`trace_id` 生成。
- **依赖**：无（纯模型，被其余所有模块依赖）。
- **接口**：见 5.3。

### 6.2 `internal/gateway`（HTTP 发布网关）

- **职责**：对外 HTTP 发布入口，参数校验、Envelope 组装、转投 broker；不做鉴权/限流（网关负责）。
- **依赖**：envelope, broker。
- **路由**：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/v1/publish` | 单条发布 |
| POST | `/v1/publish/batch` | 批量发布（上限见第 14 章 TODO） |
| GET | `/healthz` | 存活探针 |
| GET | `/readyz` | 就绪探针（依赖连通性） |
| GET | `/metrics` | Prometheus 抓取端点 |

- **请求/响应契约**：
  ```json
  // 请求
  { "topic": "order", "tag": "created", "biz_key": "order_123",
    "headers": {"app": "order-svc"}, "payload": {"order_id": 123} }
  // 响应
  { "msg_id": "...", "trace_id": "..." }
  ```
- **约束**：所有下游调用（broker.Send）显式超时；错误响应脱敏，不透传内部细节（规范第 2 节）。

### 6.3 `pkg/sdk`（Go 生产者 SDK）

- **职责**：Go 生产者易用库，屏蔽接入细节，提供发布/批量/重试。
- **依赖约束**：位于 `pkg/`，**禁止依赖 `internal/`**（规范第 9 节）。因此：
  - **默认 HTTP 网关模式**：SDK 通过 HTTP 调 `internal/gateway`，零 internal 耦合（推荐 PHP 之外的 Go 生产者使用）。
  - **可选直连 broker 模式**：直接基于 RocketMQ 客户端库（第三方）实现生产，仅复用 Envelope 的 **JSON wire 契约**（5.3），不 import internal。
- **接口草图**：
  ```go
  type Client interface {
      Publish(ctx context.Context, msg *Message) (*Result, error)
      PublishBatch(ctx context.Context, msgs []*Message) ([]*Result, error)
      Close() error
  }
  type Options struct {
      Mode      TransportMode // http | broker
      Endpoint  string        // HTTP 网关地址 或 RocketMQ 接入点
      Timeout   time.Duration // 显式超时
      Retry     RetryConfig   // 客户端侧重试
  }
  func NewClient(opts Options) (Client, error)
  ```

### 6.4 `internal/broker`（RocketMQ 5.x 适配）

- **职责**：封装 `apache/rocketmq-clients/golang`（gRPC），对上暴露与具体客户端解耦的 Producer/Consumer 抽象。
- **依赖**：envelope。
- **接口草图**：
  ```go
  type Producer interface {
      Send(ctx context.Context, e *envelope.Envelope) error
      Close() error
  }
  type MessageHandler func(ctx context.Context, e *envelope.Envelope) error
  type Consumer interface {
      Subscribe(topic, group, tag string, h MessageHandler) error // 支持运行时动态订阅
      Start(ctx context.Context) error
      Close() error // 停止拉取并等待在途处理完成（配合优雅关闭）
  }
  ```
- **约束**：连接参数（接入点、超时、重试、消费并发度、批量大小）**显式配置**，不依赖库默认值（规范第 6 节）；消费采用集群模式（consumer group）以支持水平扩展。

### 6.5 `internal/dispatcher`（分发引擎，核心）

- **职责**：作为 `broker.MessageHandler` 的落地实现，完成「幂等 → 暂停 → 路由 → 并发回调 → 重试 → DLQ → ack」全流程（时序见 4.2）。
- **依赖**：config（路由快照）、callback（HTTP 投递）、store（幂等/记录/DLQ）。
- **接口草图**：
  ```go
  type Dispatcher struct { /* config, callback, store, limiter, metrics */ }
  func New(deps Deps) *Dispatcher
  // Handle 实现 broker.MessageHandler；返回 nil 触发 ack，返回 error 触发重投。
  func (d *Dispatcher) Handle(ctx context.Context, e *envelope.Envelope) error
  ```
- **并发**：多 subscriber 回调用 `errgroup.WithContext` + `SetLimit` 受控并发；每个 worker goroutine panic recover（规范第 5 节）。
- **失败分类**（规范第 2 节）：4xx 视为业务错误不重试直接入 DLQ 并告警；5xx/网络/超时视为可恢复错误重试；配置/依赖致命错误快速失败。

### 6.6 `internal/callback`（HTTP 回调投递）

- **职责**：向单个 subscriber 投递 Envelope 的 HTTP 客户端，处理超时、状态码判定、退避重试。
- **依赖**：envelope。
- **接口草图**：
  ```go
  type Callback interface {
      Deliver(ctx context.Context, sub *Subscriber, e *envelope.Envelope) (*DeliveryResult, error)
  }
  type DeliveryResult struct {
      Status   int           // HTTP 状态码
      Latency  time.Duration // 本次投递耗时
      Attempts int           // 实际尝试次数
  }
  ```
- **约定**：2xx 视为成功；`trace_id`/`msg_id` 通过回调请求头透传给业务；回调 body 为 Envelope JSON；连接池复用（`http.Transport` 显式配置 MaxIdleConns/超时）。回调签名防伪见第 14 章 TODO。

### 6.7 `internal/canal`（BinLog 解析）

- **职责**：消费 canal topic，将 Canal 消息解析为 `Kind=binlog` 的 Envelope，再交 dispatcher。
- **依赖**：envelope, dispatcher。
- **接口草图**：
  ```go
  type Parser interface {
      Parse(raw []byte) (*envelope.Envelope, error)
  }
  ```
- **格式**：默认解析 Canal 的 **JSON FlatMessage**（Canal → RocketMQ 常用格式）；若采用 protobuf 需替换 parser 实现（第 14 章 TODO）。解析出的 `db.table`/`eventType` 用于路由匹配。

### 6.8 `internal/config`（配置中心抽象 + 热更新）

- **职责**：抽象配置来源，维护内存路由表，支持热更新与原子替换。
- **依赖**：无（被 dispatcher/broker 依赖）。
- **接口草图**：
  ```go
  type ConfigSource interface {
      Load(ctx context.Context) (*Config, error)
      Watch(ctx context.Context) (<-chan ConfigEvent, error)
  }
  type TableStore interface {
      Snapshot() *RoutingTable            // 无锁读，dispatcher 每次取最新
      Reload(cfg *Config) error           // 校验 + 重建 + 原子替换
  }
  ```
- **实现**：占位 `fileSource`（本地 yaml + fsnotify，`fsnotify` 已是间接依赖）/ `staticSource`；后期 `grpcSource` 对接自研配置中心（契约待定，第 14 章 TODO）。
- **热更新机制**：`Watch` → 校验 → 重建 `RoutingTable` → `atomic.Pointer[RoutingTable].Store`；详见第 7 章。

### 6.9 `internal/store`（持久化）

- **职责**：投递记录、死信、幂等去重、配置持久化。
- **依赖**：envelope。
- **接口草图**：
  ```go
  type DeliveryRepo interface {
      Save(ctx context.Context, r *DeliveryRecord) error
  }
  type DeadLetterRepo interface {
      Push(ctx context.Context, d *DeadLetter) error
      List(ctx context.Context, q Query) ([]*DeadLetter, error)
      Replay(ctx context.Context, id string) error
  }
  type IdempotencyStore interface {
      Seen(ctx context.Context, msgID, subscriberID string) (bool, error)
      Mark(ctx context.Context, msgID, subscriberID string) error
  }
  ```
- **实现**：MySQL（投递记录/DLQ/配置持久，唯一索引兜底幂等）+ Redis（`SETNX+TTL` 幂等热去重）。连接池显式配置容量与超时（规范第 6 节）。表结构草图见第 10 章。

### 6.10 依赖方向（禁止循环，规范第 9 节）

```text
envelope（最底层，无依赖）
   ▲
   ├── broker、callback、canal、store
   ▲
config（被依赖，自身无 internal 依赖）
   ▲
dispatcher ── 依赖 config / callback / store
   ▲
canal ── 依赖 dispatcher
gateway ── 依赖 broker
cmd/main ── 装配以上全部（唯一允许持有全局依赖图的地方）
```

## 7. 配置模型与热插拔机制

### 7.1 四类配置（数据结构草图）

```go
// Listener 监听定义：从哪里消费。
type Listener struct {
    ID      string
    Source  string // "mq" | "canal"
    Topic   string // MQ topic 或 canal topic
    Group   string // consumer group
    Tag     string // 过滤标签（可空）
    Enabled bool
}

// Route 路由定义：什么消息投给谁。
type Route struct {
    ID          string
    Match       MatchRule
    Subscribers []string // subscriber ID 列表
}

type MatchRule struct {
    Topic string // mq
    Tag   string // mq
    DB    string // canal
    Table string // canal
    Event string // canal：INSERT/UPDATE/DELETE
}

// Subscriber 订阅方：回调目标与投递策略。
type Subscriber struct {
    ID        string
    Endpoint  string            // 回调 URL
    Timeout   time.Duration     // 单次回调超时
    Retry     RetryPolicy       // 重试策略
    RateLimit int               // 并发上限（可选）
    Headers   map[string]string // 固定回调头
    Secret    string            // 回调签名密钥（TODO，见第 14 章）
}

type RetryPolicy struct {
    MaxAttempts    int
    InitialBackoff time.Duration
    MaxBackoff     time.Duration
    Multiplier     float64
}

// Pause 暂停规则：热插拔的核心，无需发版暂停消息。
type Pause struct {
    ID     string
    Scope  string // "topic" | "tag" | "subscriber"
    Target string
    Reason string
    Expire int64  // 过期时间戳（Unix 秒），0=永久
}
```

### 7.2 内存路由表与原子替换

- `RoutingTable` 为上述配置的**不可变内存快照**（预索引：按 topic/tag、按 db.table+event 建查找结构），由 `atomic.Pointer[RoutingTable]` 承载。
- dispatcher 每次 `Handle` 调 `Snapshot()` 无锁读最新表，不阻塞投递。
- 热更新：`ConfigSource.Watch` 收到 `ConfigEvent` → 校验（结构/引用完整性/endpoint 格式）→ 重建 `RoutingTable` → `Store(newTable)` 原子替换。旧快照被在途请求持有至完成，GC 自然回收。

### 7.3 ConfigSource 抽象与占位

```go
type ConfigSource interface {
    Load(ctx context.Context) (*Config, error)
    Watch(ctx context.Context) (<-chan ConfigEvent, error)
}
```

- **占位实现**：`fileSource`（本地 yaml + fsnotify）或 `staticSource`（内存），保证 gRPC 契约未定时链路可独立跑通。
- **目标实现**：`grpcSource` 对接自研配置中心（gRPC 流式 Watch），契约对齐后仅替换实现，上层无感知。
- Watch goroutine 必须 panic recover + 退出防护（`ctx.Done()` 退出，避免泄漏，规范第 5 节）。

### 7.4 动态新增 Listener 的处理

新增 Listener（新 topic/group）需 broker **运行时动态订阅**：config 变更事件→ diff 出新增/删除的 Listener → 调 `broker.Consumer.Subscribe`/取消订阅。设计要点：`Consumer.Subscribe` 支持运行时调用；若客户端库不支持动态增删订阅，则退化为「重建 consumer 实例」（实施阶段根据 `rocketmq-clients/golang` 能力确定，列入 TODO）。

## 8. 可靠性设计

| 维度 | 策略 |
| --- | --- |
| **投递语义** | at-least-once。全 subscriber 成功（或已入 DLQ）后才 ack；未 ack 会重投 → 幂等兜底 |
| **幂等** | `IdempotencyStore`，key = `msg_id + subscriber_id`；Redis `SETNX+TTL` 热去重，MySQL 唯一索引持久兜底；投递前查 `Seen`，成功后 `Mark` |
| **重试** | 指数退避：`InitialBackoff * Multiplier^n`，封顶 `MaxBackoff`，上限 `MaxAttempts`；区分可重试（网络/5xx/超时）与不可重试（4xx） |
| **DLQ** | 超重试上限/不可重试 → 死信 topic + `store.DeadLetter` 记录；支持人工/定时重放 |
| **背压** | 队列深度指标；consumer 拉取速率与 dispatcher 处理能力匹配；`SetLimit` 控并发；必要时暂停拉取 |
| **并发** | `errgroup.WithContext` + `SetLimit`；每 goroutine panic recover（消费 worker、回调、config watch） |
| **超时** | 所有外部调用（RocketMQ send/consume、HTTP 回调、Canal、MySQL、Redis、gRPC config）显式超时 |
| **失败分类** | 业务错误（4xx）→ 不重试直接 DLQ + 告警；系统错误（5xx/网络）→ 重试；可恢复 → 重试；致命 → 快速失败 |
| **顺序** | 当前不保证（全并发）；未来按 `biz_key` 分区有序的演进路径见第 14 章 TODO |

**重试退避伪代码**：

```text
for attempt in 1..MaxAttempts:
    result = callback.Deliver(sub, envelope)   // 内含单次超时
    if result.success: return OK
    if result.status in 4xx: return DLQ(不重试)
    sleep(min(InitialBackoff * Multiplier^(attempt-1), MaxBackoff))
return DLQ(超重试上限)
```

## 11. 生命周期与部署

### 11.1 启动装配（`cmd/` 扩展）

```text
InitFlag → MustInitAppConf → MustInitLog
  → 初始化 store（MySQL/Redis）
  → 初始化 config（ConfigSource.Load + 启动 Watch goroutine）
  → 初始化 broker（Producer + Consumer，按 Listener 订阅）
  → 初始化 callback / dispatcher / canal
  → 启动 HTTP gateway server（goroutine）+ broker.Consumer.Start
  → bootstrap.Heartbeat
  → bootstrap.WaitingExit(清理链...)
```

现有 `cmd/main.go` 已具备「日志初始化 + Heartbeat + WaitingExit」骨架，实施阶段按上述顺序扩展装配（建议迁至 `cmd/message-bus/main.go`，对齐规范第 9 节「每个可执行文件一个子目录」）。

### 11.2 优雅关闭顺序（接入 `bootstrap.WaitingExit` 清理链）

```text
1. 停止 HTTP gateway 接收新发布（server.Shutdown）
2. 停止 broker.Consumer 拉取新消息
3. 等待在途 dispatcher 回调完成（超时兜底 shutdown_timeout，现有配置项）
4. 关闭 config Watch、broker、callback、store 连接
5. logger.Sync
```

现有 `bootstrap` 已提供 panic 隔离 + 超时兜底 + 二次信号强退；各模块的 `Close()` 作为清理函数注册进 `WaitingExit(funs...)` 即可。

### 11.3 部署

- **无状态水平扩展**：consumer group 内多实例分担消费；配置中心统一路由；实例无本地状态（幂等走 Redis/MySQL）。
- **12-Factor**：配置来自环境变量（+ 配置中心）；容器友好。
- **Dockerfile**：多阶段构建（builder：`go build`；runtime：精简基础镜像），实施阶段落地（规范第 10 节）。

## 13. 分阶段实施路线

| 里程碑 | 范围 | 验收标准 |
| --- | --- | --- |
| **M1 生产链路** | envelope + broker(producer) + gateway(HTTP) + pkg/sdk(HTTP 模式) + 配置/日志装配 | PHP/Go 发消息入 RocketMQ，`/v1/publish` 返回 msg_id |

## 14. 假设与待确认（TODO）

1. **配置中心 gRPC 契约**：消息结构、Watch 流式协议、鉴权方式——待对齐，当前 `fileSource` 占位。

6. **Canal 投递格式**：默认 Canal JSON(FlatMessage)，若用 protobuf 需调整 parser。
7. **msg_id 生成策略**：雪花/ULID，需时钟与机器位分配方案（多实例不冲突）。
8. **批量发布上限与消息体大小限制**：`/v1/publish/batch` 批量上限、单消息体积上限待定。
9. **broker 动态订阅能力**：`rocketmq-clients/golang` 是否支持运行时增删订阅，否则退化为重建 consumer 实例（影响 7.4）。
