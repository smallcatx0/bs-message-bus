# 分布式消息总线架构设计

> 本文档从 `docs/desc.txt` 的原始需求出发，给出中台化分布式消息总线的整体架构设计，作为后续分阶段实施的蓝本。

## 1. 背景与目标

### 1.1 背景（摘自 `docs/desc.txt`）

面向以 **PHP 为主、无常驻内存**的业务线，统一收口 RocketMQ 对接的**分布式消息总线**：以中台模式提供易用 SDK、中心统一消费回调与 BinLog 变更订阅，避免 40+ 业务项目重复造轮子对接消息队列。

### 1.2 核心矛盾与设计支点

- **矛盾**：PHP-FPM 是请求级生命周期，跑不了长连接的 MQ 消费者；但它能正常收发 HTTP。
- **支点**：把 MQ 侧的全部复杂性（连接、消费、重试、路由、位点）**收口到 Go 常驻中台**，业务侧只面对两件事——**发 HTTP（生产）** 与 **收 HTTP 回调（消费）**。

### 1.3 目标能力

| 编号 | 能力 | 说明 |
| --- | --- | --- |
| G1 | 生产 SDK + 中心消费回调 | 封装易用接入屏蔽 RocketMQ 复杂度并统一消息格式；中心统一消费 + 按配置回调各服务 |
| G2 | BinLog 变更订阅 | 基于 Canal 监听 MySQL binlog，按配置规则将数据变更回调到对应业务 |
| G3 | 配置中心热插拔 | 监听、暂停消息、回调路由均由配置中心动态下发，无需发版 |

### 1.4 非目标（边界之外）

- **鉴权 / 限流**：由上游 API 网关统一负责，**服务内不实现相关中间件**（既有工程规范）。
- **业务语义处理**：中台只做「路由 + 投递」，不理解也不改写业务负载内容。
- **消息持久化存储**：消息主体持久化交由 RocketMQ；中台仅持久化投递记录/死信/幂等/配置。

## 2. 设计原则、约束与技术选型

### 2.1 工程规范约束（对齐 `项目规范.md`）

- **日志**：统一 `go.uber.org/zap`，经 `pkg/logger` 工厂接入；必须携带 `trace_id`、脱敏后的关键参数、业务 ID、`latency_ms`。禁止自行构造日志实例。
- **指标**：Prometheus，覆盖请求延迟、请求数量、错误率、goroutine 数、队列深度。
- **错误处理**：错误信息携带调试上下文但**敏感字段必须脱敏**（手机号/邮箱/密码/token/证件号）；返回外部的错误不透传内部实现细节（SQL/堆栈/下游地址）；按业务错误/系统错误/可恢复错误/致命错误四类分治。
- **并发与超时**：并发编排优先 `errgroup.WithContext` + `SetLimit`；**每个 goroutine 必须 panic recover** 并记录堆栈与上下文；**所有外部调用（HTTP、DB、RPC、MQ）必须显式超时**。
- **性能**：热点路径减少 slice 重复扩容/字符串复制/临时对象，并配 benchmark；连接池显式配置容量与超时。
- **测试**：核心逻辑覆盖率 `>= 85%`，覆盖单元/并发/边界。
- **运行时**：优雅关闭（SIGINT/SIGTERM → 停止接收 → 等待在途完成 → 释放资源）；12-Factor，配置来自环境变量、服务无状态、容器友好。
- **结构**：`cmd/` 只做装配；`internal/` 按领域分包、禁止循环依赖；`pkg/` 只放无业务依赖的通用代码。

### 2.2 架构原则

1. **抽象隔离外部依赖**：`broker`（RocketMQ）、`config`（配置中心）、`store`（MySQL/Redis）全部接口化，实现可替换、可 mock、可单测。
2. **单一职责、小而聚焦**：分发（dispatcher）与回调投递（callback）分离；模型（envelope）与传输解耦。
3. **无状态可水平扩展**：实例不持本地状态，幂等/记录走共享存储；消费按 consumer group 分担。
4. **至少一次 + 幂等**：投递语义 at-least-once，以 `msg_id` 幂等去重兜底重复。
5. **配置驱动、热插拔**：监听/路由/暂停全部由配置中心动态下发，内存路由表原子替换、无需发版。
6. **CDC 复用主链路**：Canal binlog 统一转成 Envelope，与 MQ 消息共用同一套路由/投递/死信逻辑，避免两套分发。

### 2.3 技术选型（锁定决策）

本表为经确认的架构选型基线，后续实施不得擅自偏离；变更需同步修订本表与相关模块设计。

| 事项 | 决策 |
| --- | --- |
| 语言/运行时 | Go 1.20+（现状 `go.mod` 1.23.1） |
| 生产端接入 | **proto 单一真源、双 SDK（均为交付物）**：`publish.proto` 定义 `PublishService` → 自动生成 Go gRPC stub（`pkg/publishpb`）与 gRPC-Gateway 的 HTTP/JSON 反代。**Go SDK**（`pkg/sdk`）走原生 gRPC；**PHP SDK**（`sdk/php`）封装自动生成的 HTTP/JSON（PHP-FPM 请求级生命周期不跑长连接，故走 HTTP、无需 grpc 扩展，见 1.2）。网关只维护一套 `PublishService` 实现 |
| Broker | RocketMQ **5.x**，客户端 `apache/rocketmq-clients/golang`（gRPC） |
| CDC 接入 | **Canal → RocketMQ 专用 topic**，复用 broker/dispatcher，不做 TCP 直连；**采集白名单在 Canal sink 侧过滤**（`filter.regex`），入 MQ 前完成，非白名单表不产生 MQ 消息 |
| Canal 管理 | **canal-admin 中转**：配置中心 → canal-admin REST → Canal 热加载 `filter.regex`；canal-admin 自带 MySQL（属 Canal 侧，非总线） |
| 配置中心 | 自研 **gRPC** 服务，为**路由与采集白名单的唯一真源**；`internal/config` 先做 `ConfigSource` 接口抽象 + 占位实现（本地/静态），gRPC 契约后期对齐（标 TODO，见第 14 章） |
| 投递语义 | **at-least-once + 幂等（成功后标记去重 + in-flight 并发租约锁；binlog 用确定性位点键）+ 异步重试（重试 topic + 延迟消息退避）+ 熔断 park + DLQ**；不保证顺序，分发全并发 |
| 鉴权/限流 | 由上游 API 网关统一负责，**服务内不实现中间件**（既有规范），文档划为边界外 |
| 日志/指标 | 复用 `pkg/logger`（zap）；补 Prometheus（规范第 1 节：延迟/数量/错误率/goroutine/队列深度） |
| 配置解析/存储 | viper（现状，仅本地启动参数）；**总线不持久化配置**（配置仅存于配置中心 + 总线内存态）；MySQL 仅存运维数据（投递记录/DLQ）+ Redis（幂等热去重） |
| 并发编排 | `errgroup.WithContext` + `SetLimit`（`golang.org/x/sync`） |
| CDC 组件 | Canal（MySQL binlog 订阅），经 RocketMQ 投递 |

## 3. 整体架构

### 3.1 分层架构图

```text
        ┌──────────────── 上游 API 网关（鉴权 / 限流，边界外）────────────────┐

  PHP 业务 ─sdk/php·HTTP/JSON▶ 接入层 internal/gateway （grpc-gateway 自动生成 HTTP/JSON 反代）
  Go  业务 ─pkg/sdk·gRPC────▶        │  PublishService：校验 · 组装 Envelope（生成 msg_id / trace_id）
                                 ▼
                          适配层  internal/broker  （RocketMQ 5.x gRPC）
                                 │  Producer                    ▲ Consumer
                                 ▼                               │
                       ┌──────────────  RocketMQ 集群  ──────────────┐
                       │   业务 topic            canal topic         │
                       └──────────────────────────────────────────────┘
                                 ▲                       │
   MySQL ──binlog──▶ Canal ──────┘（sink 侧 filter.regex 白名单过滤，仅白名单表投递）
                                                         │
                                                         ▼
                          核心  internal/dispatcher （分发引擎）
                                 │  路由匹配 · 暂停判定 · 熔断/去重 · 并发回调 · per-sub 异步重试/park · DLQ
                                 ▼
                          投递  internal/callback ──HTTP──▶  各 PHP 业务服务
                                 ▲
                          控制面 internal/config （ConfigSource 抽象，仅内存路由表·不落库）
                                 ▲  ①watch：监听 / 路由 / 暂停 热下发（gRPC）
                          自研配置中心（gRPC · 路由与白名单唯一真源）
                                 │  ②派生白名单（canal 路由的 db.table 集合）
                                 ▼
                          canal-admin ──REST 热加载 filter.regex──▶ Canal（源端过滤）

   运维数据 internal/store：MySQL（投递记录 / DLQ） + Redis（幂等热去重）；配置不落库
   横切：pkg/logger（zap） · Prometheus 指标 · trace_id 全链路贯穿
```

### 3.2 组件职责一览

| 组件 | 层 | 职责 | 主要依赖 |
| --- | --- | --- | --- |
| `internal/gateway` | 接入层 | `PublishService` 实现（校验、组装 Envelope、转投 broker）；同进程挂 gRPC server + grpc-gateway 自动生成的 HTTP/JSON 反代 | envelope, broker, pkg/publishpb |
| `pkg/publishpb` | 契约 | `publish.proto` 生成物：消息、gRPC stub、grpc-gateway 反代（跨边界稳定契约） | 无（生成物） |
| `pkg/sdk` | 接入层 | Go 生产者易用库，经原生 gRPC 调 PublishService，屏蔽接入细节 | pkg/publishpb（无 internal 依赖） |
| `sdk/php` | 接入层 | PHP 生产者 SDK（交付物），封装自动生成的 HTTP/JSON，屏蔽 proto/编码细节 | 无（HTTP 客户端） |
| `internal/broker` | 适配层 | RocketMQ 5.x gRPC 收发，Producer + Consumer 抽象 | envelope |
| `internal/dispatcher` | 核心 | 消费消息 → 路由 → 熔断+去重+并发回调 → 异步重试（转重试 topic）/park/DLQ → ack | config, callback, store |
| `internal/callback` | 投递 | HTTP 回调客户端，向订阅方单次投递并处理超时/状态码判定（重试由 dispatcher 异步驱动） | envelope |
| `internal/canal` | CDC | 消费**已源端白名单过滤**的 canal topic，解析 binlog → Envelope | envelope, dispatcher |
| `internal/config` | 控制面 | 配置中心抽象 + 内存路由表热更新（原子替换，**不落库**） | 无 |
| `internal/store` | 持久化 | 投递记录 / DLQ / 幂等去重（**运维数据，非配置**） | envelope |
| `internal/envelope` | 模型 | 统一消息模型与编解码（最底层，无依赖） | 无 |
| `internal/metrics` | 横切 | Prometheus 指标采集与注册 | 无 |

## 4. 核心数据流（四条时序）

### 4.1 生产流（G1 生产端）

```text
PHP: php-sdk->publish($msg)
  → SDK 组装 JSON（payload 自动 base64）POST /v1/publish（grpc-gateway 自动生成路由）
  → 反代为进程内 gRPC PublishService.Publish
  → gateway 校验 → envelope.New（msg_id 雪花/ULID、trace_id、timestamp）→ broker.Producer.Send（显式超时）
  → RocketMQ 业务 topic → 返回 PublishResponse{msg_id, trace_id} → SDK 解为 PHP 数组/对象

Go:  sdk.Publish(ctx, msg)
  → 经原生 gRPC 调同一 PublishService（契约 pkg/publishpb，零 internal 耦合）
  → 后续同上
```

要点：`trace_id` 在入口生成（或透传上游网关带入的），随 Envelope 进入 MQ，为后续消费/回调全链路追踪锚点。

### 4.2 中心消费回调流（G1 消费端，核心）

```text
RocketMQ 业务 topic
  → broker.Consumer（consumer group）拉取消息
  → dispatcher.Handle(ctx, envelope)：
      1. 解析 Envelope
      2. 暂停判定：config 快照中 Pause 是否命中 topic/tag/subscriber
      3. 路由匹配：config 快照中 Envelope → subscriber 列表
      4. 并发回调：errgroup.WithContext + SetLimit，逐 subscriber：
           a. 熔断判定：该 subscriber 熔断器为 open？→ 是：转投重试 topic（park 语义：拉长退避、
              等半开探活恢复，不即时打端点），跳过本次 Deliver（治理细节见 6.6.1）
           b. 成功去重：store.IsDelivered(msg_id, subscriber_id) 命中 → 已成功，跳过（绝不重复打）
           c. 并发互斥：store.TryLockInflight(msg_id, subscriber_id) 抢不到 → 让路（他实例在投），本周期跳过
           d. 调 callback.Deliver（单次超时，不在 Handle 内同步退避重试）
              - 2xx → store.MarkDelivered 写成功标记 + 释放 inflight 锁 + 熔断计数清零 + 投递记录异步落库
              - 失败 → 释放 inflight 锁（失败路径显式 Unlock，避免占坑到 TTL）→ 转 5
      5. 失败结果处理（投递即决，不阻塞 Handle；重试/ park 均为 per-subscriber 的 RetryTask，见 5.4）：
         - 可重试失败（网络/5xx/超时）：计入熔断滑动窗口；为该 (msg, subscriber) 产出 RetryTask，
           attempt+1、首失败时盖 FirstFailedAt；attempt < MaxAttempts → 投**重试 topic**（RocketMQ 延迟消息
           承载指数退避）；超上限 → DLQ
         - 不可重试失败（4xx）→ 直接 DLQ（死信 topic + store 记录），**不计熔断、不产 RetryTask**（业务拒绝≠端点不健康）
      6. 全部 subscriber 已决（成功 / 已转 RetryTask / 已入 DLQ）→ 返回成功 → broker ack
         （重试/park 由重试 topic 按 per-sub RetryTask 驱动、**不重跑路由**；成功标记去重兜底；
           Handle 内不做同步重试循环，源 consumer 的 invisible_duration 须覆盖最坏扇出，见第 8 章约束）
```

### 4.3 Canal 订阅流（G2）

**采集白名单在源端（Canal sink）过滤，入 MQ 前完成**，避免非目标表刷爆 MQ 后在消费端被丢弃：

```text
[配置下发]  配置中心 派生白名单（= 所有 canal 路由的 db.table 集合 → filter.regex）
           → canal-admin REST → Canal 热加载 filter.regex

[数据流]    MySQL binlog → Canal Parser（解析）
           → Canal Sink：按 filter.regex 白名单过滤（非白名单表在此丢弃，不进 store/MQ）
           → 仅白名单表投递 RocketMQ canal topic
           → broker.Consumer（canal group）拉取
           → canal.Parse：解析 Canal 消息（默认 JSON FlatMessage）
               → 提取 db / table / eventType / before / after / pk / execTime
               → 组装 Envelope{Kind: binlog, Source: "canal", Payload: BinlogEvent}
                 MsgID = 确定性位点派生键（见 5.2 P0-1），非随机生成，保证同一变更重投时 key 稳定
           → dispatcher.Handle：路由匹配按 db.table + event → 并发 HTTP 回调业务
               → 无匹配路由（传播瞬时偏差）→ 丢弃 + canal_unrouted_total 计数告警
           → 失败/重试/DLQ 逻辑与 4.2 完全一致（复用）
```

要点：
- **两层过滤**：源端白名单（Canal `filter.regex`，主过滤，省 MQ）+ 总线端路由匹配（回调权威，兜底）。二者由配置中心**同源派生**，天然一致（见 7.5）。
- Canal 不直连，统一经 RocketMQ，与主链路共用 broker/dispatcher/callback/store，只多一个 `canal.Parse` 前置解析步骤。
- 白名单派生与下发是**配置中心 + canal-admin 的职责，总线不参与**（总线只消费已过滤的 canal topic）。

### 4.4 配置热插拔流（G3）

配置变更由配置中心**一处修改、两路传播**：① 路由 → 总线（内存热替换）；② 采集白名单 → canal-admin → Canal。

```text
自研配置中心（gRPC）变更监听/路由/暂停
  ├─①（总线路由）config.ConfigSource.Watch(ctx) 收到 ConfigEvent
  │     → 校验合法性（结构/引用完整性/endpoint 格式）
  │     → 基于新 Config 重建内存 RoutingTable
  │     → atomic.Pointer[RoutingTable].Store(newTable)（原子替换）
  │     → dispatcher / broker 下一次读取 Snapshot() 即生效（无锁、无重启）
  └─②（Canal 白名单）配置中心从 canal 路由派生 db.table 白名单
        → canal-admin REST 更新 filter.regex → Canal 实例热加载（增删表不重启）

占位阶段（gRPC 契约未定）：fileSource（本地 yaml + fsnotify 监听）或 staticSource（内存静态）
```

要点：`ConfigSource` 是抽象接口，占位实现与 gRPC 实现可无缝替换；「无需发版创建监听/暂停」由配置变更 → 原子替换路由表实现。新增 Listener 涉及 broker 运行时动态订阅，见第 7.4 节；白名单派生与 canal-admin 下发见 7.5，两路传播的时序一致性见第 14 章 TODO。

## 5. 统一消息模型 Envelope

`internal/envelope` 定义的统一信封，**生产、中心消费、Canal 三条流共用**，是「统一消息格式」的落点。

### 5.1 Envelope 结构（草图）

```go
// Envelope 消息总线统一信封，贯穿生产→消费→回调全链路。
type Envelope struct {
    MsgID     string            // 全局唯一幂等键：business 用雪花/ULID；binlog 用确定性位点派生键（见 5.2），保证同一变更重投时 key 稳定
    TraceID   string            // 链路追踪 ID，全链路透传
    Topic     string            // 业务主题（canal 场景可为 db.table 派生）
    Tag       string            // 二级过滤标签（可空）
    BizKey    string            // 业务键（可选，用于查询/未来顺序分区）
    Source    string            // 来源：生产者应用名 或 "canal"
    Kind      MessageKind       // 消息类型：business | binlog
    Timestamp int64             // 生产时间（Unix 毫秒）
    Headers   map[string]string // 透传头（含回调需带的业务标识）
    Payload   []byte            // 业务负载（JSON）；binlog 场景为 BinlogEvent 序列化
}

type MessageKind string
const (
    KindBusiness MessageKind = "business"
    KindBinlog   MessageKind = "binlog"
)
```

### 5.2 BinLog 事件结构（`Kind == binlog` 时 Payload 内容）

```go
// BinlogEvent Canal 解析后的数据变更事件。
type BinlogEvent struct {
    DB          string          // 库名
    Table       string          // 表名
    EventType   string          // INSERT | UPDATE | DELETE
    Before      json.RawMessage // 变更前镜像（UPDATE/DELETE 有值）
    After       json.RawMessage // 变更后镜像（INSERT/UPDATE 有值）
    PK          string          // 主键值（幂等/查询/未来顺序键）
    ExecTime    int64           // binlog 执行时间（Unix 秒）
    GTID        string          // 全局事务 ID（MySQL gtid_set；确定性幂等首选，Canal 未开 GTID 模式时为空）
    BinlogFile  string          // binlog 文件名（Canal 采集位点，幂等兜底）
    BinlogPos   uint64          // binlog 位点（同事务内事件递增，可定位单条变更）
    EventID     int64           // Canal FlatMessage.id（Canal 生成的事件序号，兜底）
}
```

> **确定性幂等键（P0-1 修订）**：binlog 流的 `Envelope.MsgID` **不再随机生成**，而由 `canal.Parse` 依据上游位点**确定性派生**，保证同一数据库变更被 Canal 重启 / consumer 未 ack 重投 / MQ 消息重传时 key 稳定，幂等去重（成功标记，见 6.9/8）才真正生效（否则重复 msg_id 会让去重完全失效）。派生优先级：`GTID`（开启 GTID 模式）→ `BinlogFile:BinlogPos`（位点模式）→ `EventID`（Canal 事件号）→ 兜底 `hash(db.table + PK + ExecTime)`；形式：`msg_id = "binlog:" + 上述稳定坐标`（多主键表可并入 PK 集合哈希）。

### 5.3 编解码约定

- **序列化**：Envelope 整体 JSON 编码作为 RocketMQ message body。
- **属性透传**：`trace_id`、`msg_id`、`kind` 等关键头同时写入 RocketMQ message properties，便于消费端不解析 body 即可路由/追踪。
- **接口草图**：
  ```go
  func New(topic, tag string, payload []byte) *Envelope // 自动填充 msg_id/trace_id/timestamp
  func Encode(e *Envelope) ([]byte, error)
  func Decode(data []byte) (*Envelope, error)
  ```
- **wire 契约稳定性**：`pkg/sdk` 不能 import `internal/envelope`（规范第 9 节）。Go SDK、PHP SDK 与网关之间以 **`publish.proto` 单一真源**为跨边界稳定契约：由 proto 生成 Go gRPC stub 与 gRPC-Gateway HTTP/JSON 反代，两 SDK 只构造 `PublishRequest`，Envelope 的组装（msg_id/trace_id）由网关侧完成，SDK 不感知 Envelope JSON schema；proto 契约变更需重新生成并同步两侧 SDK、网关与本文档。

### 5.4 投递重试任务 RetryTask（V1·per-subscriber）

重试与 park 的**单元下沉到 `(msg_id, subscriber_id)`**：重试 topic 的消息体不再是整条 Envelope，而是一条 per-sub 的 `RetryTask`。

```go
// RetryTask per-subscriber 投递重试/挂起记录：重试 topic 的唯一消息体。
// 只承载“某 msg 对某 subscriber 的投递进度”，不参与首次扇出（首投仍走 Envelope 原路）。
type RetryTask struct {
    Envelope      *envelope.Envelope // 目标消息（作为回调 body）
    SubscriberID  string             // 唯一目标订阅方（per-sub 粒度，解耦各订阅方预算）
    Attempt       int                // 该 (msg,sub) 已实际投递次数（park 不++，仅真投递失败才 ++）
    FirstFailedAt int64              // 首失败/首 park 时间戳（Unix 毫秒），用于 MaxDwell 滞留判定
}
```

要点：
- **解耦预算**：每条 RetryTask 只对应一个 subscriber，`Attempt`/退避/park 滞留/DLQ 均 per-(msg,sub)，消除“整条 Envelope 重投→多订阅方共享 attempt、一个死订阅方连带把偶发失败的订阅方一起判 DLQ”。
- **park 不消耗 attempt**：open 期间按墙钟 `FirstFailedAt` 判 `MaxDwell`，`Attempt` 不++,修复“park 与 MaxAttempts 语义冲突”（否则长 outage 会把从未真投的消息按 attempt 耗尽提前 DLQ）。
- **不重跑路由**：重试 consumer 直接取 `RetryTask.SubscriberID` 投递，不重进路由→避免配置新增订阅方后老消息误投给它。
- **与 V2 关系**：V1 仅将「重试/park」下沉为 per-sub 记录，**首投仍走 Envelope 扇出**；V2 进一步把首投也统一为 Task-Topic（见 `docs/分布式消息总线架构演进V2.md`）。

## 6. 模块设计

每个模块给出：职责、关键接口/类型（草图）、依赖方向。所有接口以「可 mock、可单测」为设计前提。

### 6.1 `internal/envelope`（消息模型，最底层）

- **职责**：定义统一 Envelope 与 BinlogEvent，提供编解码、`msg_id`/`trace_id` 生成。
- **依赖**：无（纯模型，被其余所有模块依赖）。
- **接口**：见 5.3。

### 6.2 `internal/gateway`（发布网关：gRPC + 自动生成 HTTP/JSON）

- **职责**：实现唯一的 `PublishService`（参数校验、Envelope 组装、转投 broker）；不做鉴权/限流（网关负责）。同进程同时暴露：① **原生 gRPC**（Go SDK 直连）；② **HTTP/JSON**（PHP SDK），由 gRPC-Gateway 依据 proto 注解**自动生成反代**，转发到进程内同一 gRPC 实现，无需手写 HTTP handler。
- **依赖**：envelope, broker, `pkg/publishpb`（含 gRPC stub 与 grpc-gateway 反代生成物）。
- **契约（proto 单一真源）**：`publish.proto` 定义服务与 `google.api.http` 注解，生成物统一落 `pkg/publishpb`。
  ```proto
  service PublishService {
    rpc Publish (PublishRequest) returns (PublishResponse) {
      option (google.api.http) = { post: "/v1/publish" body: "*" };
    }
    rpc PublishBatch (PublishBatchRequest) returns (PublishBatchResponse) {
      option (google.api.http) = { post: "/v1/publish/batch" body: "*" };
    }
  }
  message PublishRequest {
    string topic = 1; string tag = 2; string biz_key = 3;
    map<string, string> headers = 4; bytes payload = 5; // 业务 JSON；protojson 下为 base64，SDK 自动编解
  }
  message PublishResponse { string msg_id = 1; string trace_id = 2; }
  ```
- **HTTP/JSON 路由（自动生成，PHP SDK 面向）**：

| 方法 | 路径 | 来源 |
| --- | --- | --- |
| POST | `/v1/publish` | proto `google.api.http` 注解自动生成 |
| POST | `/v1/publish/batch` | 同上（批量上限见第 14 章 TODO） |
| GET | `/healthz` `/readyz` `/metrics` | **非 RPC 端点，手动挂 `http.ServeMux`**（探针 + Prometheus） |

- **进程装配**：gRPC server 与 grpc-gateway mux 分端口监听（或 `cmux` 同端口按协议分流）；健康/指标端点手动注册到 gateway 的 `ServeMux`。
- **约束**：所有下游调用（broker.Send）显式超时；错误经 gRPC status 传递，grpc-gateway 自动映射为 HTTP status + 标准错误体（`{code,message,details}`），脱敏由服务端拦截器统一保证，不透传内部细节（规范第 2 节）。

### 6.3 生产者 SDK（交付物：Go + PHP，均由 proto 派生）

两套 SDK 均为对外交付物，共享 `publish.proto` 单一真源（见 5.3 / 6.2），各自封装传输与编码细节，业务侧只面对「构造消息 → 发布」。

#### 6.3.1 `pkg/sdk`（Go 生产者 SDK，原生 gRPC）

- **职责**：Go 生产者易用库，经**原生 gRPC** 调 `internal/gateway` 的 PublishService，提供发布/批量/重试。
- **依赖约束**：位于 `pkg/`，**禁止依赖 `internal/`**（规范第 9 节）。gRPC 契约生成物 `publishpb` 置于 `pkg/publishpb`：SDK 以客户端 stub 引入、网关（internal）以服务端实现引入，共享同一契约而 SDK 零 internal 耦合。
- **接口草图**：
  ```go
  type Client interface {
      Publish(ctx context.Context, msg *Message) (*Result, error)
      PublishBatch(ctx context.Context, msgs []*Message) ([]*Result, error)
      Close() error // 释放底层 grpc.ClientConn
  }
  type Options struct {
      Endpoint string        // gRPC 网关地址（host:port）
      Timeout  time.Duration // 单次 RPC 显式超时（映射为 context deadline）
      Retry    RetryConfig   // 客户端侧重试（幂等前提下对可恢复错误退避）
      // 可选：grpc.DialOption 透传（TLS、keepalive、拦截器等）
  }
  func NewClient(opts Options) (Client, error) // 建立 grpc.ClientConn 并封装 PublishServiceClient
  ```
- **约束**：每次 RPC 显式超时，不依赖 gRPC 默认；连接复用单一 `grpc.ClientConn`（多路复用），`Close()` 释放；错误经 gRPC status 转为脱敏错误（规范第 2 节）。

#### 6.3.2 `sdk/php`（PHP 生产者 SDK，HTTP/JSON）

- **职责**：PHP 生产者易用库，封装 gRPC-Gateway **自动生成**的 HTTP/JSON 接口，提供 `publish/publishBatch`；PHP-FPM 请求级生命周期不跑长连接，故走 HTTP 而非原生 gRPC（见 1.2），无需 grpc 扩展。
- **契约来源**：HTTP 路由、请求/响应 JSON schema 均由 `publish.proto`（`google.api.http` 注解）自动派生，**不手写、不单独维护**；proto 变更 → 重新生成网关 → PHP SDK 随之对齐。
- **实现要点（草图）**：
  ```php
  // 基于 cURL/Guzzle 的薄封装
  $client = new MessageBus\Client(['endpoint' => 'http://gateway:8080', 'timeout' => 2.0]);
  $res = $client->publish(['topic'=>'order','tag'=>'created','biz_key'=>'order_123',
                           'headers'=>['app'=>'order-svc'],'payload'=>['order_id'=>123]]);
  // $res['msg_id'] / $res['trace_id']
  ```
  - **payload 编码**：proto `bytes payload` 经 protojson 为 base64；SDK 内部自动对 payload（数组/JSON 串）做 `json_encode + base64`，业务侧无感。
  - **字段命名**：wire 为 protojson 默认（camelCase），SDK 屏蔽映射，对外暴露稳定 PHP 风格键名。
  - **超时/重试**：每次 HTTP 请求显式超时；幂等前提下对可恢复错误（5xx/网络）退避重试。
  - **错误处理**：将 grpc-gateway 标准错误体（`{code,message,details}`）转为 PHP 异常，message 已脱敏（规范第 2 节）。

### 6.4 `internal/broker`（RocketMQ 5.x 适配）

- **职责**：封装 `apache/rocketmq-clients/golang`（gRPC），对上暴露与具体客户端解耦的 Producer/Consumer 抽象。
- **依赖**：envelope。
- **接口草图**：
  ```go
  type Producer interface {
      Send(ctx context.Context, e *envelope.Envelope) error
      // SendDelayed 投递到指定 topic 并延后可见：承载 per-sub RetryTask 的指数退避与 park
      // （RocketMQ 延迟消息/延迟等级；接口化以便换 Kafka 时降级为多级 retry topic，见 V2 §8）。
      SendDelayed(ctx context.Context, topic string, body []byte, delay time.Duration) error
      Close() error
  }
  type MessageHandler func(ctx context.Context, e *envelope.Envelope) error
  // RetryHandler 消费重试 topic 的 per-sub RetryTask（不重跑路由，直投目标订阅方）。
  type RetryHandler func(ctx context.Context, t *RetryTask) error
  type Consumer interface {
      Subscribe(topic, group, tag string, h MessageHandler) error // 支持运行时动态订阅
      SubscribeRetry(topic, group string, h RetryHandler) error   // 重试/park topic
      Start(ctx context.Context) error
      Close() error // 停止拉取并等待在途处理完成（配合优雅关闭）
  }
  ```
- **约束**：连接参数（接入点、超时、重试、消费并发度、批量大小）**显式配置**，不依赖库默认值（规范第 6 节）；消费采用集群模式（consumer group）以支持水平扩展。
- **不可见时长（invisible_duration / receipt handle）显式约束**（关键，否则未 ack 会提前重投形成放大）：
  - 源 consumer：须 ≥ 单条 Handle 最坏墙钟 ≈ `ceil(N_matched_subscribers / perMessageSetLimit) × max(Subscriber.Timeout) + Redis 往返 + 余量`；
  - 重试 consumer：单条 RetryTask 只投 1 个 subscriber → ≥ `max(Timeout) + 余量`；
  - 均须落在 RocketMQ 客户端可续期(receipt handle renew)能力范围内；即便超时误重投，也因 per-sub `Attempt` + 成功标记而不致错（仅浪费）。

### 6.5 `internal/dispatcher`（分发引擎，核心）

- **职责**：作为 `broker.MessageHandler` 的落地实现，完成「暂停 → 路由 → 熔断/去重/并发互斥+并发回调 → 异步重试（转重试 topic）/DLQ → ack」全流程（时序见 4.2，重试与治理见第 8 章）。**Handle 内不做同步退避重试**，可重试失败转投重试 topic 后即 ack。
- **依赖**：config（路由快照）、callback（HTTP 投递）、store（幂等/记录/DLQ）。
- **接口草图**：
  ```go
  type Dispatcher struct { /* config, callback, store, perMsgLimiter, inflightGate(实例级回调总闸), breaker(每实例内存), metrics */ }
  func New(deps Deps) *Dispatcher
  // Handle 实现 broker.MessageHandler；返回 nil 触发 ack，返回 error 触发重投。
  func (d *Dispatcher) Handle(ctx context.Context, e *envelope.Envelope) error
  ```
- **并发**：每条消息扇出用 `errgroup.WithContext` + `SetLimit`（消息内并发）；**另设实例级回调总闸**（全局 semaphore `max_inflight_callbacks`，跨所有在途消息共享），防「M 条并发消息 × SetLimit」无界 in-flight 打满连接池/拖垮全实例。每个 worker goroutine panic recover（规范第 5 节）。
- **失败分类**（规范第 2 节）：4xx 视为业务错误不重试直接入 DLQ 并告警（不计熔断）；5xx/网络/超时视为可恢复错误，为该 (msg,subscriber) 产出 RetryTask 转投重试 topic 异步重试（per-sub 预算，见 5.4）；配置/依赖致命错误快速失败。

### 6.6 `internal/callback`（HTTP 回调投递）

- **职责**：向单个 subscriber 投递 Envelope 的 HTTP 客户端，处理单次超时与状态码判定（重试/退避上移到 dispatcher 的异步重试模型，见第 8 章）。
- **依赖**：envelope。
- **接口草图**：
  ```go
  type Callback interface {
      Deliver(ctx context.Context, sub *Subscriber, e *envelope.Envelope) (*DeliveryResult, error)
  }
  type DeliveryResult struct {
      Status  int           // HTTP 状态码
      Latency time.Duration // 本次投递耗时（供熔断慢调用率与指标用）
  }
  ```
- **约定**：2xx 视为成功；`trace_id`/`msg_id` 通过回调请求头透传给业务；回调 body 为 Envelope JSON；连接池复用（`http.Transport` 显式配置 MaxIdleConns/超时）。
- **回调签名（配置驱动，按 `Subscriber.Auth.Mode` 分派；**V1 仅实现 `static_header`**，`none`/`hmac` 预留扩展接口，见第 14 章）**：
  - `none`：不签名，仅透传 trace/msg 头（内网可信场景）。
  - `static_header`：向 `Auth.Header` 写入固定 `Auth.Token`（如 `X-Callback-Token`），业务侧比对；简单但有重放风险。
  - `hmac`：简单动态签名，`sign = HMAC-SHA256(Auth.Secret, timestamp + "\n" + nonce + "\n" + body)`，经 `X-Callback-Timestamp`/`X-Callback-Nonce`/`X-Callback-Sign` 头下发，业务侧用同密钥重算并校验（含时间窗/nonce 防重放，不属 V1，留待后续版本，见第 14 章）。
  - 密钥/token 属敏感配置，日志需脱敏（规范第 2 节）。

### 6.6.1 订阅方健康治理（熔断 / park / 半开探活）

> 前提：**接受消息被拖慢**，以换取“不再反复投递”。治理作用于**单个 subscriber 维度**，不牵连同消息其他订阅方。

- **熔断器**：per-subscriber、每实例内存维护（本质是本地资源保护，不要求跨实例强一致；重启清空、重触发即恢复）。状态机 `closed → open → half-open → closed`。
- **触发口径**：滑动窗口内 **错误率**（超时/连接失败/5xx）**+ 慢调用率**（延迟 > `SlowCallDuration`）任一越界即 open。⚠️ 只看错误率会漏掉“每 30s 超时但最终 2xx”的**慢而不死**端点——它照样吃光连接池/协程，必须由慢调用率兜住。**4xx 不计入熔断**（业务拒绝内容，非端点不健康）。
- **open 期间的处置（park 优先于 DLQ，均产 per-sub RetryTask，见 5.4）**：
  - 命中 open 的 (msg, sub) **不即时打端点**，产出一条 RetryTask 转投重试 topic 并**拉长退避**（park），等半开探活恢复后再投；**park 不递增 `Attempt`**（避免与 MaxAttempts 预算冲突），滞留按墙钟 `FirstFailedAt` 判定；
  - 仅当 `now - FirstFailedAt > MaxDwell`（最大滞留）才落 DLQ，避免一次下游长故障把 DLQ 灌爆。
- **半开探活（三态准入）**：`OpenTimeout` 起（下限 500ms）转 half-open，**自适应退避**（每次仍失败按 `BackOffFactor` 递增，封顶 `MaxOpenTimeout`）。准入逻辑：`closed` 全放行；`open` 全 park；`half-open` **仅放行 `HalfOpenMaxProbe=1` 条探针、其余仍 park**（防恢复瞬间并发打穿）。探针**借用真实待发消息**（无需下游专设健康端点、不产生合成流量），成功即 `ConsecutiveSuccess` 计数达标转 closed，失败退回 open。
- **与去重协同**：见第 8 章——熔断挡“反复打将死端点”，成功标记挡“重复打已成功订阅方”，二者叠加 + per-subscriber RetryTask 重试粒度，把“反复投递”的有害部分基本消掉。
- **跨实例一致性**：park 消息经重试 topic 由任意实例消费，各实例熔断器独立计时/计数——刚重平衡出的新实例可能尚未 open 而先投递（失败后再触发本实例熔断），恢复探测亦可能落在状态不同的实例上。属 per-instance 熔断的固有软收敛，重试 + 成功标记兜底，不影响正确性，仅延迟恢复数拍。
- **配置**：`Subscriber.Breaker`（`BreakerConfig`，见 7.1），由配置中心下发、可热调。

### 6.7 `internal/canal`（BinLog 解析）

- **职责**：消费**已源端白名单过滤**的 canal topic，将 Canal 消息解析为 `Kind=binlog` 的 Envelope，再交 dispatcher。**采集白名单过滤在 Canal sink 侧完成（见 4.3 / 7.5），本模块不承担过滤，只做解析。**
- **依赖**：envelope, dispatcher。
- **接口草图**：
  ```go
  type Parser interface {
      Parse(raw []byte) (*envelope.Envelope, error)
  }
  ```
- **格式**：默认解析 Canal 的 **JSON FlatMessage**（Canal → RocketMQ 常用格式）；若采用 protobuf 需替换 parser 实现（第 14 章 TODO）。解析出的 `db.table`/`eventType` 用于路由匹配。
- **防御性兜底**：若解析出的 `db.table` 在路由表无匹配（白名单/路由传播瞬时偏差），交 dispatcher 丢弃并计数告警（`canal_unrouted_total`），不视为错误重试。

### 6.8 `internal/config`（配置中心抽象 + 热更新）

- **职责**：抽象配置来源，维护**内存态**路由表，支持热更新与原子替换。**配置中心是唯一真源，总线不把配置落库**；本模块也**不负责向 Canal 下发白名单**（那是配置中心 + canal-admin 的职责，见 7.5）。
- **依赖**：无（被 dispatcher/broker 依赖）。
- **接口草图**：
  ```go
  type ConfigSource interface {
      Load(ctx context.Context) (*Config, error)
      Watch(ctx context.Context) (<-chan ConfigEvent, error)
  }
  type TableStore interface {
      Snapshot() *RoutingTable            // 无锁读，dispatcher 每次取最新
      Reload(cfg *Config) error           // 校验 + 重建 + 原子替换（仅内存，不落库）
  }
  ```
- **实现**：占位 `fileSource`（本地 yaml + fsnotify，`fsnotify` 已是间接依赖）/ `staticSource`；后期 `grpcSource` 对接自研配置中心（契约待定，第 14 章 TODO）。
- **热更新机制**：`Watch` → 校验 → 重建 `RoutingTable` → `atomic.Pointer[RoutingTable].Store`；详见第 7 章。

### 6.9 `internal/store`（持久化）

- **职责**：投递记录、死信、幂等去重（均为**运维数据，非配置**；配置不落库，见 6.8）。
- **依赖**：envelope。
- **接口草图**：
  ```go
  type DeliveryRepo interface {
      Save(ctx context.Context, r *DeliveryRecord) error
  }
  type DeadLetterRepo interface {
      Push(ctx context.Context, d *DeadLetter) error
      List(ctx context.Context, q Query) ([]*DeadLetter, error)
      Replay(ctx context.Context, id string) error
  }
  type IdempotencyStore interface {
      // IsDelivered 读“投递成功标记”：true 表示该 (msg,sub) 曾成功投递 → 跳过，绝不重复打。
      IsDelivered(ctx context.Context, msgID, subscriberID string) (bool, error)
      // MarkDelivered 仅在 Deliver 返回 2xx 后写成功标记（SET + TTL，覆盖重投窗口）。
      // 关键：必须“成功后”才写——若在投递前占坑，失败重试会被误判“已投”而永久投不出去（at-most-once 陷阱）。
      MarkDelivered(ctx context.Context, msgID, subscriberID string) error
      // TryLockInflight 可选并发互斥：短 TTL 租约锁（SETNX+PX），防多实例同时首投同一 (msg,sub)。
      // 抢不到返回 false → 让路，本周期跳过；失败/完成路径 UnlockInflight 或随 TTL 自动释放，不永久占坑。
      TryLockInflight(ctx context.Context, msgID, subscriberID string, ttl time.Duration) (acquired bool, err error)
      // UnlockInflight 释放 in-flight 租约（失败路径显式调用以尽快允许重试；成功路径可省略，由 IsDelivered 接管）。
      UnlockInflight(ctx context.Context, msgID, subscriberID string) error
  }
  ```
- **实现**：Redis 承载幂等两件套——**成功标记** `delivered:{msg}:{sub}`（SET+TTL，投递成功后写，是去重权威）+ **in-flight 租约锁** `inflight:{msg}:{sub}`（SETNX+短 TTL，可选，消并发双投）；MySQL 投递记录**仅审计**、DLQ 持久（`delivery_record` 的 `(msg_id, subscriber_id)` 唯一索引作数据完整性约束，**不作为幂等兜底**——投递成功后异步写，无法覆盖“已投未落库”窗口，见第 8 章）。连接池显式配置容量与超时（规范第 6 节）。表结构草图见第 10 章。

## 7. 配置模型与热插拔机制

### 7.1 四类配置（数据结构草图）

```go
// Listener 监听定义：从哪里消费。
type Listener struct {
    ID      string
    Source  string // "mq" | "canal"
    Topic   string // MQ topic 或 canal topic
    Group   string // consumer group
    Tag     string // 过滤标签（可空）
    Enabled bool
}

// Route 路由定义：什么消息投给谁。
type Route struct {
    ID          string
    Match       MatchRule
    Subscribers []string // subscriber ID 列表
}

type MatchRule struct {
    Topic string // mq
    Tag   string // mq
    DB    string // canal
    Table string // canal
    Event string // canal：INSERT/UPDATE/DELETE
}

// Subscriber 订阅方：回调目标与投递策略。
type Subscriber struct {
    ID        string
    Endpoint  string            // 回调 URL
    Timeout   time.Duration     // 单次回调超时
    Retry     RetryPolicy       // 重试策略
    RateLimit int               // 并发上限（可选）
    Breaker   BreakerConfig     // 订阅方熔断/探活配置（见 6.6.1）
    Headers   map[string]string // 固定回调头
    Auth      CallbackAuth      // 回调鉴权/签名方案（配置驱动，见 6.6）
}

// CallbackAuth 回调签名配置：由配置中心按 subscriber 下发，方案可插拔。
type CallbackAuth struct {
    Mode   string // "none" | "static_header" | "hmac"（可扩展）
    Header string // static_header：头名，如 "X-Callback-Token"
    Token  string // static_header：写死的固定 token
    Secret string // hmac：签名密钥；sign=HMAC-SHA256(secret, ts+nonce+body)
}

type RetryPolicy struct {
    MaxAttempts    int
    InitialBackoff time.Duration
    MaxBackoff     time.Duration
    Multiplier     float64
}

// BreakerConfig 订阅方熔断治理配置（per-subscriber，见 6.6.1；值为建议默认，最终见第 14 章 TODO）。
type BreakerConfig struct {
    Enabled            bool
    ErrorRateThreshold float64       // 滑动窗口错误率阈值（如 0.5）
    SlowCallRate       float64       // 慢调用率阈值（如 0.5）
    SlowCallDuration   time.Duration // 判定“慢”的延迟阈值（≈ 单次 Timeout）
    WindowSize         int           // 滑动窗口最小样本数
    OpenTimeout        time.Duration // open→half-open 基础间隔（下限，如 500ms）
    BackOffFactor      float64       // 半开间隔随失败递增系数（自适应，封顶 MaxOpenTimeout）
    MaxOpenTimeout     time.Duration // 半开间隔上限（如 30s）
    HalfOpenMaxProbe   int           // half-open 并发探针数（=1，防恢复打穿）
    MaxDwell           time.Duration // 熔断 park 最大滞留，超则入 DLQ
    ConsecutiveSuccess int           // 连续成功多少次后转 closed（如 1）
}

// Pause 暂停规则：热插拔的核心，无需发版暂停消息。
type Pause struct {
    ID     string
    Scope  string // "topic" | "tag" | "subscriber"
    Target string
    Reason string
    Expire int64  // 过期时间戳（Unix 秒），0=永久
}
```

### 7.2 内存路由表与原子替换

- `RoutingTable` 为上述配置的**不可变内存快照**（预索引：按 topic/tag、按 db.table+event 建查找结构），由 `atomic.Pointer[RoutingTable]` 承载。
- dispatcher 每次 `Handle` 调 `Snapshot()` 无锁读最新表，不阻塞投递。
- 热更新：`ConfigSource.Watch` 收到 `ConfigEvent` → 校验（结构/引用完整性/endpoint 格式）→ 重建 `RoutingTable` → `Store(newTable)` 原子替换。旧快照被在途请求持有至完成，GC 自然回收。

### 7.3 ConfigSource 抽象与占位

```go
type ConfigSource interface {
    Load(ctx context.Context) (*Config, error)
    Watch(ctx context.Context) (<-chan ConfigEvent, error)
}
```

- **V1 实现**：`fileSource`（本地 yaml + fsnotify）为第一版**唯一落地**实现（配置中心 gRPC 契约本轮不对齐，见第 14 章）；`staticSource`（内存）用于测试。
- **后续版本**：`grpcSource` 对接自研配置中心（gRPC 流式 Watch），契约对齐后仅替换实现，上层无感知。
- Watch goroutine 必须 panic recover + 退出防护（`ctx.Done()` 退出，避免泄漏，规范第 5 节）。

### 7.4 动态新增 Listener 的处理

新增 Listener（新 topic/group）需 broker **运行时动态订阅**：config 变更事件→ diff 出新增/删除的 Listener → 调 `broker.Consumer.Subscribe`/取消订阅。设计要点：`Consumer.Subscribe` 支持运行时调用；若客户端库不支持动态增删订阅，则退化为「重建 consumer 实例」（实施阶段根据 `rocketmq-clients/golang` 能力确定，列入 TODO）。

### 7.5 Canal 采集白名单：派生与下发（源端过滤）

**目标**：只让「会被回调的表」的 binlog 进入 MQ，避免 MQ 被非目标表刷爆后在消费端丢弃。

- **唯一真源**：配置中心只维护**一份路由配置**（`Route`，含 canal 类型的 `MatchRule.DB/Table`）。
- **派生白名单**：Canal 采集白名单 = 所有 `Source=canal` 的 Route 的 `db.table` 集合，转成 Canal `filter.regex`（逗号分隔正则，如 `db1\.tbl_a,db1\.tbl_b,db2\.tbl_c`）。
- **下发路径**：配置中心 → **canal-admin REST** → Canal 实例热加载 `filter.regex`（增删表无需重启 Canal）。
- **职责边界**：派生与下发由**配置中心 + canal-admin** 完成，**消息总线不参与**（总线只消费已过滤的 canal topic，也不落库配置）。
- **两层过滤**：源端白名单（Canal，主过滤省 MQ）+ 总线端路由匹配（回调权威）；因白名单由路由派生，二者天然一致。
- **一致性时序**：白名单与路由由配置中心同批变更，传播存在瞬时偏差属正常——
  - 新增表：总线路由先生效而 Canal 未采集 → 无消息空转无害；Canal 先采集而总线未路由 → 总线丢弃并计数（`canal_unrouted_total`）。
  - 删除表：反向同理，偏差窗口内少量消息被总线丢弃，不影响正确性（at-least-once + 无路由即丢弃）。
- **canal-admin 的 MySQL**：属 Canal 生态自身存储，与「总线不落库」不冲突。

## 8. 可靠性设计

| 维度 | 策略 |
| --- | --- |
| **投递语义** | at-least-once。源消息扇出后即 ack（每个 (msg,sub) 成功 / 转 per-sub RetryTask / 入 DLQ 均视为已决）；未 ack（进程崩溃等）由 RocketMQ 重投 → 成功标记去重兜底。**Handle 内不做同步重试**，且源 consumer 的 invisible_duration 须按 6.4 约束覆盖最坏扇出 |
| **幂等（成功去重）** | 两件套：**成功标记** `IsDelivered/MarkDelivered`（Redis，**仅投递成功后 SET+TTL**）为去重权威——投递前读到即跳过，**绝不再打已成功订阅方**；**in-flight 短租约锁** `TryLockInflight`（SETNX+PX，可选）串行化多实例对同一 (msg,sub) 的并发首投。⚠️ **不可用“投递前一次性 SETNX 永久占坑”代替成功标记**：那样一旦本次失败，重试会被自己的占坑判为“已投”而永久投不出去（退化成 at-most-once）。**binlog 流用确定性位点键作 msg_id**（见 5.2 P0-1）。**Redis 故障按 fail-open**（放行投递、记 WARN + `idempotency_error_total`）。**注：标记只减少重复、非 exactly-once；TTL 过期后的迟到重投仍可能重复，业务侧必须自身幂等（原则 4）**。**性能**：同一消息多订阅方的 `IsDelivered` 用 pipeline/MGET 合并、`MarkDelivered` 异步 pipeline 写；`TryLockInflight` 默认可关。**锁错误策略**：`TryLockInflight` 返回 error 按“视为抢到”放行（fail-open），去重仍由 `IsDelivered` 兜底 |
| **重试（异步·per-sub）** | **不在 Handle 内同步退避**。可重试失败：为该 `(msg, subscriber)` 产出 **RetryTask**（见 5.4）投专用**重试 topic**，以 RocketMQ **延迟消息**承载指数退避（`InitialBackoff * Multiplier^Attempt` 封顶 `MaxBackoff`），`Attempt` 只计真投递失败（park 不++）；重试 consumer **按 RetryTask.SubscriberID 直投该订阅方、不重跑路由**（各订阅方预算独立，避免共享 Attempt 连带误判 DLQ）。与主链路解耦，单条慢/故障消息不占用消费 worker |
| **订阅方健康（熔断/park）** | per-subscriber 熔断器（每实例内存，closed/open/half-open）。**触发 = 错误率 + 慢调用率**（超时/连接失败/5xx 计入；**4xx 不计**，业务拒绝≠端点不健康），纯错误率会漏掉“慢而不死”端点拖垮资源。open 期间不即时投递，该 (msg,sub) 产 RetryTask 走 park：**转重试 topic 拉长退避、`Attempt` 不++**（接受拖慢），`now - FirstFailedAt` 超 `MaxDwell` 才入 DLQ（避免灌爆 DLQ）。half-open **自适应间隔（≥500ms 起、随失败递增封顶）放行单条探针**（借真实待发消息，避免恢复瞬间并发打穿）。治理细节见 6.6.1 |
| **DLQ** | 不可重试（4xx）或超出 `MaxAttempts`（重试 topic 再次失败达上限）或熔断滞留超 `MaxDwell` → 死信 topic + `store.DeadLetter` 记录；支持人工/定时重放 |
| **背压** | 队列深度指标；consumer 拉取速率与 dispatcher 处理能力匹配；`SetLimit` 控并发；慢/故障订阅方经**熔断 park**（转重试 topic 长退避）不占用 worker；必要时暂停拉取 |
| **并发** | `errgroup.WithContext` + `SetLimit`；每 goroutine panic recover（消费 worker、回调、config watch） |
| **超时** | 所有外部调用（RocketMQ send/consume、HTTP 回调、Canal、MySQL、Redis、gRPC config）显式超时 |
| **失败分类** | 业务错误（4xx）→ 不重试直接 DLQ + 告警；系统错误（5xx/网络/超时）→ 转重试 topic 异步重试；致命 → 快速失败 |
| **顺序** | 当前不保证（全并发）；未来按 `biz_key` 分区有序的演进路径见第 14 章 TODO |

**投递与异步重试伪代码（首投扇出 + per-sub RetryTask 重试；投递即决，不同步 sleep）**：

```text
// ① 源消息扇出（首次 Handle）：对每个匹配 subscriber 独立走 dispatchAttempt，attempt=0
for sub in route(envelope):
    go dispatchAttempt(sub, envelope, attempt=0, firstFailedAt=0)   // errgroup SetLimit + 实例级 inflight 闸
// 全部 (msg,sub) 已决（成功/转 RetryTask/DLQ）→ ack 源

// ② 重试/park consumer：按 RetryTask 直投其目标订阅方，不重跑路由
for t in retryTopic:
    dispatchAttempt(t.subscriber, t.envelope, t.attempt, t.firstFailedAt)

// ③ 单 (msg,sub) 投递即决逻辑（首投与重试共用）
func dispatchAttempt(sub, env, attempt, firstFailedAt):
    switch breaker.State(sub):
      case open:
        ts = firstFailedAt>0 ? firstFailedAt : now()
        if now() - ts < MaxDwell:
            retryTopic.SendDelayed(retryTask{sub,env,attempt,ts}, longBackoff)   // park：attempt 不++
        else:
            dlq.Push(env, sub, "熔断滞留超 MaxDwell")
        return
      case half-open:
        if !breaker.AllowProbe(sub):            // 超过 HalfOpenMaxProbe 条
            retryTopic.SendDelayed(retryTask{sub,env,attempt,firstFailedAt}, openProbeInterval)
            return
        // 否则放行该条作为探针，继续投递流程

    if store.IsDelivered(env.msg, sub): return               // 已成功，绝不重复打
    if !store.TryLockInflight(env.msg, sub, lockTTL): return // 他实例在投则让路；锁 error→视为抢到放行(fail-open)

    result = callback.Deliver(sub, env)           // 单次超时；占用实例级 max_inflight_callbacks 名额
    switch:
      2xx:  store.MarkDelivered(env.msg, sub); breaker.OnSuccess(sub); store.SaveAsync(rec); return
      4xx:  store.UnlockInflight(env.msg, sub); dlq.Push(env, sub, "4xx 不可重试"); return   // 不计熔断
      else: // 可重试失败（网络/5xx/超时）
            store.UnlockInflight(env.msg, sub); breaker.OnFailure(sub)
            next := attempt + 1                    // 只有真投递失败才 ++
            if next < MaxAttempts:
                delay = min(InitialBackoff*Multiplier^next, MaxBackoff)
                ts = firstFailedAt>0 ? firstFailedAt : now()
                retryTopic.SendDelayed(retryTask{sub,env,next,ts}, delay)
            else:
                dlq.Push(env, sub, "超 MaxAttempts")
```

**消费者时长与并发约束**：
- 源 consumer `invisible_duration ≥ ceil(N_matched/SetLimit) × max(Timeout) + 余量`；重试 consumer ≥ `max(Timeout) + 余量`（见 6.4）。
- 实例级 `max_inflight_callbacks` 全局信号量约束跨消息并发回调总量；`broker.Consumer` 并发拉取数与之匹配，避免慢订阅方堆积拖垮全实例。

## 10. 存储设计（草图，不落 `sql/`）

### 10.1 MySQL 表（仅运维数据，**配置不落库**）

> 配置（Listener/Route/Subscriber/Pause + Canal 白名单）唯一真源是配置中心，总线仅内存态持有，**不设配置表**；以下仅为投递运维/审计数据。

```text
delivery_record  投递记录
  id, msg_id, subscriber_id, topic, status, attempts, latency_ms, created_at, updated_at
  唯一索引：(msg_id, subscriber_id)  -- 完整性约束/审计去重（幂等以 Redis 成功标记为准，见 6.9/8）
  索引：(topic, created_at)、(subscriber_id, status)

dead_letter  死信
  id, msg_id, subscriber_id, topic, kind, payload, reason, attempts, first_failed_at, created_at, replayed_at
  唯一索引：(msg_id, subscriber_id)  -- DLQ 去重（同一 msg 对同一订阅方仅一条死信，兜现 6.6.1 承诺）
  索引：(topic, created_at)、(replayed_at)
```

### 10.2 Redis 键

```text
delivered:{msg_id}:{subscriber_id} → "1"    TTL      # 投递成功标记（成功后 SET；去重权威，TTL 覆盖重投窗口）
inflight:{msg_id}:{subscriber_id}  → owner  短TTL    # 并发互斥租约锁（SETNX+PX；可选，防多实例同投）
ratelimit:{subscriber_id}          → 令牌桶         # 可选，订阅方级限流
```

### 10.3 连接池（显式配置，规范第 6 节）

- MySQL：`MaxOpenConns`/`MaxIdleConns`/`ConnMaxLifetime` 显式配置。
- Redis：`PoolSize`/`DialTimeout`/`ReadTimeout`/`WriteTimeout` 显式配置。
- 保留与归档策略（delivery_record/DLQ 清理周期、Redis TTL 取值）见第 14 章 TODO。

## 11. 生命周期与部署

### 11.1 启动装配（`cmd/` 扩展）

```text
InitFlag → MustInitAppConf → MustInitLog
  → 初始化 store（MySQL/Redis）
  → 初始化 config（ConfigSource.Load + 启动 Watch goroutine）
  → 初始化 broker（Producer + Consumer，按 Listener 订阅）
  → 初始化 callback / dispatcher / canal
  → 启动 HTTP gateway server（goroutine）+ broker.Consumer.Start
  → bootstrap.Heartbeat
  → bootstrap.WaitingExit(清理链...)
```

现有 `cmd/main.go` 已具备「日志初始化 + Heartbeat + WaitingExit」骨架，实施阶段按上述顺序扩展装配（建议迁至 `cmd/message-bus/main.go`，对齐规范第 9 节「每个可执行文件一个子目录」）。

### 11.2 优雅关闭顺序（接入 `bootstrap.WaitingExit` 清理链）

```text
1. 停止 HTTP gateway 接收新发布（server.Shutdown）
2. 停止 broker.Consumer 拉取新消息
3. 等待在途 dispatcher 回调完成（超时兜底 shutdown_timeout，现有配置项）
4. 关闭 config Watch、broker、callback、store 连接
5. logger.Sync
```

现有 `bootstrap` 已提供 panic 隔离 + 超时兜底 + 二次信号强退；各模块的 `Close()` 作为清理函数注册进 `WaitingExit(funs...)` 即可。

### 11.3 部署

- **无状态水平扩展**：consumer group 内多实例分担消费；配置中心统一路由；实例无本地持久状态（幂等走 Redis/MySQL）。**例外：熔断器为可重建的本地“软”内存态**（重启即清、重触发即恢复），不承担投递正确性，不影响水平扩展语义。
- **12-Factor**：配置来自环境变量（+ 配置中心）；容器友好。
- **Dockerfile**：多阶段构建（builder：`go build`；runtime：精简基础镜像），实施阶段落地（规范第 10 节）。

## 13. 分阶段实施路线

| 里程碑 | 范围 | 验收标准 |
| --- | --- | --- |
| **M1 生产链路** | proto/publishpb 生成 + envelope + broker(producer) + gateway(gRPC + grpc-gateway HTTP/JSON) + pkg/sdk(gRPC) + sdk/php(HTTP/JSON) + 配置/日志装配 | Go 经 gRPC、PHP 经 HTTP/JSON 发消息入 RocketMQ，均返回 msg_id |
| **M2 中心消费回调** | broker(consumer + 重试 topic/SubscribeRetry) + dispatcher(熔断+去重+per-sub RetryTask) + callback + store(成功标记/DLQ) + config(占位 fileSource)；新建重试 topic + invisible_duration/实例级并发闸配置 | 消息回调到 mock 业务；失败经 per-sub 异步重试退避后入 DLQ；成功标记去重生效；慢/故障订阅方被熔断 park 不拖垮 worker |
| **M3 Canal 订阅** | canal 解析 + canal topic 消费 + 按 db.table/event 路由 + 无路由丢弃兜底（依赖配置中心/canal-admin 已下发源端白名单） | binlog 变更回调业务，非白名单表不入 MQ，复用主链路投递 |
| **M4 配置中心对接** | config grpcSource 替换占位 + 动态增删 Listener + 暂停热生效 + 配置中心派生白名单→canal-admin 下发链路打通 | 不发版创建监听/暂停消息；新增表自动进白名单并被采集 |
| **M5 可观测与压测** | Prometheus 指标 + trace 贯穿 + benchmark + 优雅关闭全链 + Dockerfile | 指标齐全、压测达标、关闭无 goroutine 泄漏 |

每阶段配套单测（核心逻辑 >= 85%）+ 热点路径 benchmark（规范第 6/7 节）；变更后按 AGENTS.md「变更影响验证」输出影响范围与风险等级。

### 13.1 任务级拆分与执行顺序（决策，经确认）

里程碑落到可独立验收的开发任务，按**契约先行、接口先行 + mock 驱动、底层无依赖模块先落**三原则排序（依赖依据见 6.10）：

1. **阶段 0 = `internal/config`（T7）提前于 M1**：自身无 internal 依赖、零外部基础设施依赖（纯内存可测），且 Route/Subscriber/Pause 数据结构是 dispatcher/callback/broker 的共同契约，先立住避免下游各自臆造。相对 M1 交付时「config 占位属 M2」的口径前移，其余里程碑顺序不变；M4 的 grpcSource 因此只是换实现。设计落地见 D02 [配置抽象与热更新-design.md](history/配置抽象与热更新-design.md)（已完成归档）。
2. **M1 内部顺序**：envelope（+统一脱敏函数，落 `pkg/mask`）→ proto/publishpb 契约 → broker(Producer) ∥ callback → gateway → pkg/sdk ∥ sdk/php → 集成验收（唯一硬阻塞：需真实 RocketMQ 实例，开发期可用内存 fake 不阻塞）。
3. **M2 内部顺序**：store ∥ broker Consumer/SubscribeRetry → dispatcher（依赖 store/config 接口，mock 可先行开发，真实环境只影响集成验收）→ 集成验收。
4. **M3**：canal 解析 + canal topic 消费路由；Canal/canal-admin 环境此前不需准备。
5. **M4**：先做 TODO 9（rocketmq-clients 动态订阅能力）spike，结论落设计文档后再启动 grpcSource 与动态 Listener。
6. **M5**：metrics 补全 + benchmark + Dockerfile + 关闭全链回归。**例外：指标注册骨架提前到 gateway/dispatcher 开发时即埋点**，避免后补指标回改全部模块。

任务粒度与设计文档对应关系：Dnn 按里程碑建文档、任务作章节（D02=M1 前置的阶段 0；D03=用户直接发起的配置消费侧窄竖切——dispatcher 路由消费契约与热更新装配提前落地，见 [history/分发与路由-design.md](history/分发与路由-design.md)，已归档；M1 生产链路自 D04 起依此类推）；TODO 8（批量/体积上限）在 M1 契约章拍板。

## 14. 假设与待确认（TODO）

1. **配置中心契约**：决策——**第一版（V1）仅实现 `fileSource`**（本地 yaml + fsnotify，见 7.3）；`ConfigSource` 抽象保留，配置中心 gRPC 契约（消息结构 / Watch 流式协议 / 鉴权）本轮不对齐，留待后续版本仅替换实现、上层无感知。
2. **回调签名**：决策——**第一版（V1）仅实现 `static_header`**（向约定头写死固定 token、业务侧比对，见 6.6 / 7.1）；`none`/`hmac`（动态签名、时间窗/nonce 防重放）仅预留接口，不在 V1 落地。
3. **顺序性**：决策——**不保证有序**，分发全并发（与 2.3 投递语义、6.5 一致）；若未来需按 `biz_key` 有序，再引入 RocketMQ 顺序消息 + dispatcher 分区串行化，属新需求不在本版范围。
4. **暂停语义**：Pause 命中时是丢弃、暂存后补投、还是仅停止拉取？需明确。
5. **存储容量与保留策略**：delivery_record/DLQ 归档与清理周期；Redis 幂等 TTL 取值。
6. **Canal 投递格式**：默认 Canal JSON(FlatMessage)，若用 protobuf 需调整 parser。
7. **msg_id 生成策略**：business 走雪花/ULID，需时钟与机器位分配方案（多实例不冲突）；**binlog 已确定改为确定性位点派生键**（GTID→binlog file+pos→Canal EventID→兜底哈希，见 5.2 P0-1），使幂等去重对重投生效；建议 business 直接锁定 **ULID** 避免引入 worker-id 注册中心依赖。
8. **批量发布上限与消息体大小限制**：`/v1/publish/batch` 批量上限、单消息体积上限待定。
9. **broker 动态订阅能力**：`rocketmq-clients/golang` 是否支持运行时增删订阅，否则退化为重建 consumer 实例（影响 7.4）。
10. **canal-admin 对接细节**：配置中心 → canal-admin 的 REST 契约（实例/`filter.regex` 更新接口、鉴权）、白名单派生规则（`db.table` → Canal 正则的转义与合并）、Canal 实例热加载时延与失败重试。
11. **白名单/路由一致性时序**：新增/删除表时两路传播（Canal 白名单 vs 总线路由）的偏差窗口是否需强顺序（如「先下发白名单再放行路由」），当前按「无路由即丢弃」容忍偏差，需确认可接受。
12. **proto 代码生成流水线**：`publish.proto` → `pkg/publishpb`（go/go-grpc/grpc-gateway）的生成脚本与 CI 校验（生成物是否入库、工具链版本锁定）；PHP SDK 与生成 HTTP/JSON 契约的对齐方式（是否据 proto 自动生成 PHP 客户端/DTO，还是手写薄封装）。
13. **多 subscriber 共享 ack 的放大**：V1 已用 **per-subscriber RetryTask**（见 5.4）把「重试/park」下沉到 (msg,sub) 粒度 + 熔断 park + 成功标记去重，消除「整条源消息反复重投牵连其余订阅方」。**仍存留的 V1 限制**：首投仍在一条源消息上扇出（慢订阅方延长单条 Handle、靠 invisible_duration 兜底）。V2 的 **Task-Topic（首投也 per-sub + durable-then-ack）** 为连扇出/拉取开销与首投耦合也消掉的进一步解，见 `docs/分布式消息总线架构演进V2.md`；**V2 不实施**。
14. **熔断/探活参数默认值**：`BreakerConfig` 的阈值（错误率/慢调用率）、`OpenTimeout` 下限（500ms 起）、自适应封顶 `MaxOpenTimeout`、`MaxDwell`（park 最大滞留→DLQ）需按业务 SLA 与压测定；park 依赖“接受拖慢”前提，需确认各订阅方可容忍的延迟上限。
15. **delivered 标记 TTL 与重投窗口**：成功标记 TTL 须覆盖「源重投 + 重试 topic 最大延迟」总窗口，取值待压测定；过期后的迟到重投仍可能重复投递（业务侧幂等兜底，见原则 4）。
