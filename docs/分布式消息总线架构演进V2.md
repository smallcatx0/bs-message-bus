# 分布式消息总线架构演进 · V2（投递扇出与 ack 前置）

> 本文档记录消息总线的 **V2 演进方向**，是对 `docs/分布式消息总线架构设计.md`（V1）中「多 subscriber 共享一个 ack」遗留问题的解法。
> **定位为演进蓝本，V1 不实施**；V1 现有设计为 at-least-once + 成功标记去重 + per-sub RetryTask 异步重试 topic + 熔断 park + DLQ，源扇出全部 (msg,sub) 已决后 ack 源。
> 遵循 `项目规范.md`：本文只做**设计**，不含实现代码；接口/流程均为草图，落地以实施阶段代码与 DDL 为准。
> 未决项统一收敛在第 12 章「假设与待确认」。

---

## 1. 定位与适用边界

| 项 | 说明 |
| --- | --- |
| 状态 | **V2 演进方向**，暂缓实施 |
| 触发条件 | V1 上线后，单条消息扇出到多 subscriber、且存在**慢/故障订阅方**时，出现「源消息被整条反复重投、已成功订阅方被重复打」的放大问题，且该放大无法靠幂等彻底消除（重投消耗、invisible_duration 调优压力） |
| 与 V1 关系 | V1 已消除「Handle 内同步重试」的阻塞问题（转异步重试 topic）；V2 进一步**解开多 subscriber 与源消息 ack 的耦合** |
| 不做 | V1 阶段不引入 task topic、不改 ack 语义，避免过早复杂化 |

---

## 2. 背景：V1 的进展与遗留

V1 已将**稳态重试/park 下沉为 per-subscriber 的 RetryTask**（见 V1 文档 5.4）+ 熔断 park + 成功标记去重，消除了“订阅方稳态失败时整条源消息反复重投、其余已成功订阅方被反复重打”。

但 V1 **首投**仍是「**一条源消息 → 扇出给全部 subscriber → 全部已决后才 ack 源**」，多 subscriber 共享同一 ack 位点，遗留：

- **崩溃窗口**：若在“部分 RetryTask 尚未 durable”时实例崩溃，源未 ack → RocketMQ 重投整条源 → 向**所有**订阅方重新扇出（已成功者靠去重兜底，但白白消耗回调/去重资源）；
- **首投时长被最慢订阅方牵制**：源 consumer 的 `invisible_duration` 须覆盖最坏扇出耗时，配置脆弱；
- 毒/慢订阅方在首投阶段仍与 healthy 订阅方共享一次消费处理。

**根因**：投递状态（per-subscriber）在**首投**仍绑定在传输单元（per-source-message）上。V2 的思路即把两者彻底解耦——**首投也走 per-sub Task**。

---

## 3. 核心方案：扇出投递任务 + ack 前置（durable-then-ack）

### 3.1 一句话定义

把「一条源消息扇出给 N 个 subscriber」拆成「**先为每个 subscriber 生成一条持久化的投递任务（DeliveryTask），任务 durable 之后再 ack 源消息**」；此后重试、退避、死信**全部以 task 为单位由总线驱动**，与源消息彻底无关。

> **铁律（决定成败）**：ack 源消息的时机 = 「扇出的 task 已全部 durable」之后。绝不能「先 ack 源、再异步落投递意图」——那样 ack 与落库之间进程崩溃会造成**消息永久丢失**（源已 gone，MQ 不再重投）。

### 3.2 语义迁移：at-least-once 不是取消，而是下沉一层

```text
V1：at-least-once 守护在「源消息」层（源未 ack 则整条重投）
V2：at-least-once 守护下沉到「per-subscriber 投递任务」层
     源消息：produce task 成功后即 ack（源只被消费一次，重复也只是重复生产 task，可去重）
     task 消息：成功/DLQ 后才 ack；未 ack 由 consumer group 自动重投给存活实例
```

MQ 仍是可靠性层（多副本、重投），只是把守护对象从「源消息」换成「task 消息」，因此 V2 **没有**把可靠性从「MQ 兜底」降级成「总线代码兜底」。

### 3.3 关键组件

| 组件 | V2 角色 |
| --- | --- |
| 源 consumer | 拉源消息 → 解析 Envelope → 路由匹配出 subscriber 列表 → 批量 produce N 条 task → 全部 ack 成功后 ack 源 |
| **DeliveryTask** | per-(msg_id, subscriber_id) 的投递任务，承载一次回调的全部上下文与 `attempt` 计数；落**专用 task topic** |
| task consumer | 消费 task → 成功标记去重（投递前查 IsDelivered，成功后 MarkDelivered）→ 单次 HTTP 回调 → 成功 ack task / 可重试失败转 retry（延迟）/ 不可重试或超上限入 DLQ |
| retry 机制 | task 级延迟重投（RocketMQ 延迟消息承载指数退避），attempt+1 |
| DLQ | task 达上限或不可重试 → 死信 topic + `store.DeadLetter`，集中可查可重放 |

## 4. 数据流（时序）

```text
[源阶段] 源 consumer
  RocketMQ 业务 topic / canal topic
    → broker.Consumer 拉源消息
    → dispatcher 解析 Envelope → config 快照路由匹配 → subscriber[]（N 个）
    → 为每个 subscriber 构造 DeliveryTask{msg_id, subscriber_id, envelope, attempt=0}
    → producer.SendBatch(task topic, N tasks)           // 批量 produce，一次网络往返
    → 全部 task produce 成功 → ack 源消息                // durable-then-ack
       （produce 部分失败 → 不 ack 源 → 源重投 → 重新扇出；task 成功标记去重）

[投递阶段] task consumer（独立 consumer group）
  DeliveryTask 到达
    → store.IsDelivered(msg_id, subscriber_id)   // 投递前查成功标记，已投则跳过（成功后才 MarkDelivered；勿 SETNX-before-deliver，否则重试被自己占坑误判“已投”）
    → callback.Deliver(task) 单次 HTTP 回调（单次超时，不同步 sleep）
    → 成功  → store 记录投递(异步) → ack task
    → 4xx   → DLQ.Push(task) → ack task                     // 不可重试
    → 可重试失败(网络/5xx/超时)：
         attempt < MaxAttempts → retryTopic.Send(task.attempt+1, deliverAfter=backoff) → ack task
         否则                  → DLQ.Push(task) → ack task

[恢复] task 未 ack（实例崩溃/重平衡）→ consumer group 自动把该 task 分给存活实例重驱动（成功标记去重）
```

要点：源阶段只做「解析 + 路由 + 批量 produce + ack」，快且不阻塞；慢订阅、重试风暴、DLQ 全隔离在 task 阶段。

## 5. 可靠性与崩溃窗口分析

`P` = task produce durable，`A` = 源消息 ack，`D` = task 投递成功并 ack。

| 崩溃点 | 状态 | 结果 | 安全性 |
| --- | --- | --- | --- |
| P 之前 | 源未 ack | 源重投 → 重新扇出 | ✅ 安全（at-least-once） |
| P 之后、A 之前 | task 已落、源未 ack | 源重投 → **重复 produce task** → task 层成功标记去重 | ✅ 安全（重复但无害） |
| A 之后、D 之前 | 源已 ack、task 未 ack | consumer group 重投 task 给存活实例 → 重驱动 | ✅ 安全 |
| （对照）A 之前未落 task（先 ack 后异步落） | 源已 gone、意图未持久 | **永久丢失** | ❌ 禁止 |

结论：只要守住「**durable-then-ack**」，V2 全程 at-least-once 无丢失窗口；重复由**成功标记（`MarkDelivered`，仅投递成功后写）**统一收敛（**勿用 SETNX-before-deliver**：否则未 ack 重投会被自己占坑误判跳过而丢投，退化为 at-most-once）。

## 6. 前置依赖（V2 落地必须先具备）

1. **幂等去重为承重墙**：V2 里「重复 produce task」是常态，全靠成功标记 `IsDelivered/MarkDelivered`（仅投递成功后 SET+TTL）去重。注：不能误用“投递前一次性 SETNX 占坑”——那样崩溃/失败后 task 未 ack 重投会被自己占坑误判“已投”而丢投；V1 已按此修正（见 V1 6.9）。
2. **binlog 流确定性 msg_id**：canal 的 `Envelope.MsgID` 用位点派生键（见 V1 文档 5.2 / P0-1），否则 task 扇出后重投的 msg_id 不稳定，去重失效。V1 已修订。
3. **`Attempt` 落点**：V1 已在 per-sub `RetryTask` 内部实现投递计数（见 V1 5.4，未污染 Envelope）；V2 沿用该思路以独立 `DeliveryTask.attempt` 承载首投+重试，仍属总线内部、不进对外 Envelope/proto。
4. **`internal/broker` 抽象支持批量 produce + 延迟投递 + 独立 task/retry consumer group**：Producer 需暴露 `SendBatch` 与「deliverAfter/延迟等级」；抽象保持 broker 可替换。

## 7. 写放大量化与缓解

扇出把「1 consume + 1 ack」变为「1 consume + N produce + N task-consume + N ack」。以 10k msg/s × 3 订阅估算 ≈ **3 万 produce/s + 3 万 task-consume/s**。

- **判断**：这是健康 MQ 集群的常规负载（几十万条小消息/s 量级），**非真实瓶颈**。
- **主缓解手段 = 批量 produce**（`SendBatch` 把一条源的 N 个 task 合并为一次网络往返），放大问题基本被抹平。
- 需新增 topic 运维：**task / retry** 两类（source/DLQ 已有）；topic 数量与配额可控。

---

## 8. Broker 选型影响（RocketMQ vs Kafka）

V2 把「逐条 ack / 不可见时长 / 原生重试队列」等 RocketMQ 强项**转成总线应用层逻辑**，于是两者在「可靠 produce + consumer group consume + 前进式提交」这层核心能力上**大体等价**，Kafka 从「不合适」变为「可用、相当」。

| 差异点 | V2 下是否仍是选 RocketMQ 的理由 |
| --- | --- |
| 逐条 ack / invisible_duration | ❌ 不再是决定性差异（统一前进式提交 + 失败重投 task） |
| 原生 per-group 重试队列 + DLQ | ⚠️ 弱化（重试/DLQ 总线自建，MQ 只是少写代码） |
| Broker 端 tag 过滤 | ⚠️ 轻微（Kafka 无服务端过滤，topic 拆分/客户端过滤可代偿） |
| **延迟/定时消息（退避载体）** | ✅ **仍是 RocketMQ 的关键优势**：Kafka 无原生延迟，需「多级 retry topic + 定时器搬运」或「把退避时钟搬到总线（Redis ZSet/调度器）」 |

**结论**：V2 缩小差距但缩不到零；唯一还没被填平的是**延迟消息**。若团队本就用 RocketMQ（V1 已锁定、生态成熟、原生延迟白捡），无换的理由；若重度 Kafka 基建且乐意自建退避时钟，Kafka 可行且相当。**用 `internal/broker` 把延迟/批量语义接口化，保证 broker 可替换**，别让延迟消息调用散落各处。

## 9. 被否决的替代方案（记录决策，避免重走）

### 9.1 本地磁盘 append-only WAL 替代 MQ 承接 task 持久化

提议：扇出 task 不落 MQ，改「顺序写本地盘（参照 Kafka message log）」。

**否决理由**：

1. **击穿无状态原则**：ack 源后 task 唯一副本落在单实例本地盘 → K8s 重调度/节点故障使 task **搁浅或丢失**；consumer group 重平衡下存活实例看不到死掉实例的本地盘，需自研跨实例归属（一致性哈希/租约）+ 恢复扫描器。
2. **Kafka 类比不完整**：Kafka 顺序日志敢当唯一真相，靠的是 **ISR 多副本复制**；单节点本地盘没有这层网。「顺序日志」恰恰是**支持用 MQ**的论据——一旦你补齐分段/索引/保留/复制/回放，就是在重新实现一遍 Kafka/RocketMQ。
3. **省的是伪瓶颈**：3 万 produce/s 本不是 MQ 瓶颈（见第 7 章，批量即可抹平），拿可靠性换非瓶颈的性能，赔率差。
4. **DLQ/退避无处安放**：task 落本地会牵出「DLQ 分散各实例本地、运维不可见不可重放」，仍需回落到 MySQL/Redis，复杂度反升。

**可保留的正确用法**：把顺序 WAL 作为 **MQ 之前的生产端持久缓冲（store-and-forward 削峰）**，缓冲项在「确认已刷入 MQ」后才 GC，MQ 始终是真相——此为可选优化，非主干。

## 11. 从 V1 迁移到 V2（改动点清单）

> V2 是叠加演进，非推倒重来。落地时同步修订 V1 文档以下处：

- **4.2 / 6.5**：ack 语义由「全部 subscriber 已决后 ack 源」改为「扇出 task durable 后 ack 源」；Handle 拆成「源扇出阶段」与「task 投递阶段」两条链。
- **6.4 broker**：Producer 增补 `SendBatch` 与延迟投递；Consumer 增补 task topic 的独立 consumer group 订阅。
- **6.9 store / 8**：`delivery_record` 明确为「task 已决后的异步审计」；task 的 durable 由 MQ（task topic）承担，不落 MySQL。
- **5.4/V1 RetryTask → 新增 DeliveryTask**：attempt 由 task 专属结构承载（沿用 V1 RetryTask 思路，见 V1 5.4），不进对外 Envelope/proto（源侧业务无感）。
- **3.1 / 3.2 / 12 目录**：新增 `internal/dispatcher` 的扇出/投递两阶段说明，task/retry topic 装配。
- **8 投递语义**：注明 at-least-once 守护层级从源消息下沉到投递任务。
- **13 里程碑**：作为 V2 阶段（如 **M6 投递扇出解耦**）排期，验收 = 毒订阅方不再牵连整条源消息重投、已成功订阅方不重复收、task 未 ack 可被他实例接管重驱动。

## 12. 假设与待确认（TODO）

1. **`Attempt` 落点**：置于 Envelope 还是独立 DeliveryTask 结构？是否进 proto/对外 SDK（倾向：总线内部字段，业务 SDK 无感）。
2. **task 扇出与源 ack 的原子性**：`SendBatch` 部分成功如何处置（建议：任一 task produce 失败即不 ack 源、整体重投，靠成功标记去重）；批量大小与超时。
3. **task 幂等 TTL**：Redis 成功标记的 TTL 需覆盖「源重投 + task 重投」最大时间窗，取值待压测定。
4. **topic 规模**：是否按 subscriber 维度拆分 task topic，还是单 task topic + header 区分（影响隔离性与运维）。
5. **canal 流扇出**：canal 的 db.table 变更可能命中多 subscriber，同样走 task 扇出；确定性 msg_id 已在 V1 落地，task 层沿用。
6. **延迟消息跨 broker 抽象**：`internal/broker` 的「延迟投递」接口如何在 Kafka 路线下降级为「多级 retry topic 搬运」或「外部时钟」，保持可替换。
7. **背压联动**：`task_topic_depth` 达阈值时，源 consumer 是否需主动降速（暂停拉取）以免 task 无限堆积。
